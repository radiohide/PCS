Windows system-history application, Rust + Tauri. The executable is a development build. [Collector acceptance matrix](docs/collector-coverage.md) records implemented fields, real-machine results and all remaining work against the 66-item catalog.

## Current implementation

- Square-edged dark/light desktop: overview, ingestion-order timeline with source timestamps, current objects, snapshot comparison, actual plugin/channel health and retention settings.
- Current objects support database-wide literal search (identity, attributes, source and scope), category/source filters, recent-change windows, stable sorting, counts and pagination. Details expand below the selected row. Schema 4 stores change-observation and successful-observation times independently of prunable history; existing objects initially show unknown times, with successful observation updated on the next complete snapshot and change time on the next actual change. Category defaults to the source namespace, with services/drivers separated. Advanced property filters and deleted-object browsing remain future work.
- Per-user named-pipe daemon with current-user/SYSTEM ACL, fixed trusted EXE collectors, Job Object cleanup, bounded protocol lines/output and per-domain timeouts. Not an installed Windows SCM service.
- SQLite transactional checkpoint/event storage, complete-snapshot differences, durable replay receipts, explicit gaps, default 5 GB rolling history and optional unlimited retention. Required current state and replay metadata survive history pruning and can eventually exhaust a capped store.
- Eleven inventory jobs: machine software; basic system/Shell; system, security, network, storage, startup, desktop, virtualization, applications and configured scopes. Expanded domains define 79 automatic sources, not 79 completed logical collectors.
- Twenty-three persisted EventLog channels with checkpoint validation and allowlisted fields. System/Application run each polling round; one additional channel rotates per round. No audit policy changes or Sysmon installation.
- Native Rust NTFS USN V2/V3 reader, per-volume journal/cursor checks and own database-file ID exclusion. Fixed drive-letter volumes only; full path reconstruction is pending. No USN journal is created, cleared or modified.
- Optional scoped file/ACL/ADS/hash, portable application and selected-process module inventories. Optional local Docker Desktop and Mihomo metadata; these remain off until configured. File content version storage is not implemented.
- EVTX batch import with resume and idempotent replay. No Prefetch/Amcache parser yet.

The header provides a frontend-only Auto refresh / Paused switch and Load latest button. Each launch defaults to automatic refresh with the existing three-second status/plugin polling and collection-completion page refresh. Pausing stops scheduled page refreshes but keeps connection checks and native backend recovery active; explicit navigation, filtering and actions still work. Load latest reads the current page once without collecting or resuming automation; timeline/object filters and unsaved plugin intervals remain intact. The connection label remains live while page refresh is paused. Run `node scripts/check-front-refresh.cjs` to verify pause/manual/resume and in-flight status handling.

Timeline readable details use a wider reading pane, compact event facts and collapsible evidence metadata. Snapshot records show aligned before/after fields in a shared scroll viewport, with changed/added/removed highlights and a differences-only filter. Arrays compare by index; masked values remain indeterminate. Non-snapshot logs keep single-column source messages and event fields. Run `node scripts/check-snapshot-diff.cjs` for comparison semantics.

## Build and run

Run `./build.ps1 -CargoArgs @('build','--workspace','--examples')`, then `./build.ps1 -CargoArgs @('build','--workspace')`. Both are needed: the first compiles examples, the second is the one that leaves the workspace binaries in `target/debug`. Build the separate desktop Cargo workspace through the same entry point with `-Project apps/desktop/src-tauri`, so both workspaces share one toolchain resolution and one linker selection. The verified desktop build uses the GNU Windows target.

The Rust toolchain is external and is never taken from PATH: pass `-ToolsRoot <dir>`, where `<dir>` contains `cargo\bin\cargo.exe`, or set `$env:PCSCOPE_TOOLS`. `-Check` reports the resolved cargo, rustc, linker and whether the selected MinGW distribution provides `libgcc.a`. That last line matters: Rust's `x86_64-pc-windows-gnu` std is linked against libgcc, which LLVM-MinGW does not ship, so an llvm-mingw bin directory cannot link this target (`lld: error: unable to find library -lgcc_eh`); a GNU `mingw64\bin` is selected first and the linker is named explicitly in `CARGO_TARGET_X86_64_PC_WINDOWS_GNU_LINKER`.

Run `./scripts/stage-dev.ps1` after both builds, while the old development executables are closed. It preserves an existing `dist/dev/collector-options.json`. Run `./scripts/open-preview.ps1 -Bundle ./dist/dev` to prepare a runnable application directory and open the preview. Subsequent launches can use the generated “打开 PCScope” shortcut; backend startup and recovery are automatic. WebView2 Runtime is required. New-program data defaults to the `native-v1` subdirectory of Tauri's per-user local application directory; `PCSCOPE_DATA_DIR` overrides it. IPC and replacement are bound to that resolved directory's filesystem identity plus the current user SID. The daemon and write-side CLI reject existing databases without the new-program marker before upgrading/writing them. Probe calls require an explicit `PCSCOPE_DATA_DIR`; graceful shutdown: set it to the desired instance's directory, then run `dist/dev/pcscope-probe.exe shutdown`.

The SIHost page configures exact process names (default `sihost`) in the current user/session and shows native module observations plus associated disk-file changes. A separate bounded worker enumerates modules every 60 seconds, shares nonrecursive directory notifications, checks known-file metadata every 300 seconds and schedules content/signature verification separately (3600 seconds or after a relevant change). Automatic and manual watch lists are independent. Previously observed files remain tracked after the target exits; a file change is not proof that loaded memory changed or that the next startup must fail. Sources keep the scoped collector's existing controls. See [runtime acceptance](docs/refactor/acceptance/SIHost-runtime-file-monitor.md) for verified cases and remaining limits.

The collector page documents all 13 execution units and supports persisted per-plugin automatic enable/disable, intervals and one-shot runs. Defaults remain 300 seconds for inventory and 10 seconds for EventLog/USN. Intervals now begin after completion (minimum 30 seconds for inventory, 10 for logs, maximum 7 days), using monotonic deadlines checked every second. Enabled jobs run on daemon startup. Saving a setting resets its idle deadline; running work finishes and uses the updated interval. Disabling skips queued automatic work and retains history. A one-shot run is allowed while disabled and does not re-enable automation. Inventory jobs serialize in one lane and logs in another; manual requests during a busy lane fail clearly instead of accumulating. Configuration lives in SQLite settings under `plugin_schedule`; runtime result/timing displays cover the current daemon session. `collector-options.json` still configures source scope, not schedules. Sources overlap between some execution units, so disabling one unit does not disable other units that inspect related data.

Plugin cards default to a compact row with the name, saved enable state and an immediate enable/disable button. The Details button reveals descriptions, interval settings, a one-shot action, runtime results and the source table. Toggling automation preserves the saved interval and any unsaved interval draft. Each plugin also displays an expandable source table: collection item name, concrete interface/data source, and collection method. The catalog contains 133 rows across 13 plugins, including all 23 event channels, registry paths/views, CIM classes, cmdlets, COM, files and optional local runtime APIs. These describe implemented sources, not successful access on the current machine. Maintain `apps/desktop/ui/plugin-sources.js` alongside collectors; run `node scripts/check-plugin-sources.cjs` to check fixed PowerShell source IDs, certificate locations, plugin coverage and event channel coverage.

An EventLog round still reads System/Application plus one rotating secondary channel, at most 128 records each; this is polling, not OS-event-triggered scheduling. USN reads at most eight 16 KiB batches per volume per round. Busy sources can outpace this development configuration. `pcscope-probe.exe plugin-control` verifies settings, validation and a disabled one-shot run, then restores the scoped plugin's original configuration.

EVTX: `dist/dev/pcscope-cli.exe import-evtx <database> <local.evtx>`. Do not use direct-write CLI commands against the daemon's active database. The selected input EVTX file is not automatically counted in the managed history quota.

## Verified on this machine

Timeline and current objects share `apps/desktop/ui/collection-catalog.json`, generated from the source descriptions by `node scripts/build-collection-catalog.cjs`. Stable item IDs split Shell and logon-startup registrations using object identity paths; source-wide gaps and unknown registrations keep explicit fallback categories. USN journal identity/exclusion operations are implementation details, not separate object types. Unknown plugin sources remain visible. Rust embeds the same catalog used by the UI; changing it requires rebuilding the service and desktop.

Both views filter the full database by collection item before pagination, and search includes translated item names. `timeline_search` supports category, item, record-kind and literal text filters, with a filtered cursor and all-history facets. The timeline still orders by ingestion sequence and shows source timestamps. Object rows show item, object name, key attributes and observation times. Deterministic summaries describe observed before/after changes, never equating snapshot discovery/disappearance with installation/deletion. Original data and source/scope remain in details. Run `node scripts/check-collection-view.cjs` and `pcscope-probe.exe collection-view` for display and read-only live IPC checks.

- Seventeen Rust tests cover twelve storage cases (including persisted plugin settings and collection-item filtering/paging), two scheduler cases and three USN parsing/resume cases. Strict Clippy does **not** pass on this tree: `cargo clippy --workspace --all-targets -- -D warnings` reports 14 lints, all in `crates/contracts` (`adapters/network.rs`, `adapters/virtualization.rs`, `adapters/security.rs`, `adapters/event.rs`, `adapters/desktop.rs`, `semantics.rs`, `sensitive.rs`, `query.rs`). None of them come from the current work, and [N01](docs/refactor/acceptance/N01-source-baseline.md) records the run with the toolchain that produced it; R09 §8 had already flagged this claim as unreproducible.
- Event projection tests cover source/provider isolation, account/session/process mappings, omitted secrets and DTD rejection.
- Scoped-file fixture tests cover metadata, owner/DACL, ADS metadata, hashing and preserving old state when a root is unavailable.
- Domain messages replay without duplicate records. A 16-record test EVTX imports once and reimports zero records.
- All eleven inventory jobs complete; IPC queries/comparison, explicit source gaps, USN poll health, duplicate-instance rejection and graceful shutdown pass. Latest integration database: 15,597 current objects (counts change with runtime).
- Security log, USN volume access, BitLocker, Secure Boot, LSA rights and several configuration sources are permission-limited on this machine. Hyper-V management is absent and Spooler unavailable. These are gaps, not successful empty inventories.

## Still required

Read [the per-collector matrix](docs/collector-coverage.md): field-level gaps remain, including full file path indexing, non-NTFS notifications, ETW/live subscriptions, content versions, additional vendor adapters and privilege-dependent real-machine acceptance. Plugin manifest enforcement/configuration UI, SCM installation/boot startup, privilege separation, installer/update/rollback, backup/restore and a 72-hour soak also remain unfinished. This build cannot yet be called complete or lossless monitoring.
