# 待决：文件身份从哪来

日期：2026-09-12。状态：**待决策**，阻塞 S14（文件与访问控制）。本文只陈述问题与选项，不代为决定。

## 1. 问题

六个类型把「文件身份」当作身份的一部分，而**没有任何快照采集端发出它**。

| 类型 | 用法 | 键 |
| --- | --- | --- |
| `file.watched_file` | `file_identity` 策略 | `volume_identity`、`file_id` |
| `desktop.shortcut` | 同上 | 同上 |
| `software.portable_registration` | 同上 | 同上 |
| `file.watched_directory` | 同上（**且没有任何来源**，见第 5 节） | 同上 |
| `file.acl_entry` | `composite_native`，其中一个键名为 `file_identity` | `file_identity`、`trustee`、`access_mask` |
| `file.alternate_data_stream` | 同上 | `file_identity`、`stream_name` |

采集端实际发的是**路径**与文件元数据（大小、时间、属性、所有者、DACL、ADS 列表、哈希）。路径**不是**文件身份：文件改名或移位后路径就变了，而身份策略选 `file_identity` 正是为了这一点。类型自己的说明也写着路径用于展示。

**当前后果**（已知，非推测）：S14 未开始，S20 已落地——每一个快捷方式都是**暂定身份**。受监控文件与便携软件同理。暂定身份不是错误结果，但一个全部暂定身份的类型在实际使用中很难用：改名后会被当成两个对象。

**R02 明令禁止适配器自行调用 Windows 补采**（「不另行调用 Windows 获取缺失的东西」）。因此适配器**不能**自己去取卷标识与文件 ID。这是本问题必须由外部决定的原因。

## 2. 已有的先例：USN 插件已经在发这个值

`pcscope.usn.{drive}` 的事件里带着 `file_id` 与 `volume`（`plugins/usn/src/main.rs`）。也就是说**这个值在系统里并非取不到**，只是快照路径上没有取。这既说明方案 A 可行，也说明若采用方案 B，同一个文件在两条链路上的身份会分道扬镳。

## 3. 选项

### 方案 A：采集端补发文件身份

在扫描文件的三个位置补上 `volume_identity`（卷序列号）与 `file_id`：

1. `domains/scoped.ps1` 的 `Scan-Root`（便携软件 + 受监控文件的根扫描）；
2. 受监控文件的单文件扫描；
3. `domains/desktop.ps1` 的快捷方式遍历。

**做法：** 需要一个原生调用（`GetFileInformationByHandle` 取卷序列号与文件索引）。项目内已有先例：`plugins/powershell-adapter/domains/IdentityNative.cs` 就是通过 `Add-Type` 加载的小型 C# helper。

- 代价：新增/扩展一个 C# helper，改三个扫描函数，重新生成样例；属于**采集端改动**，按 R07 归 `existing-runtime` 工作线，需要与对应整合责任人确认。
- 收益：六个类型的身份成立；USN 与快照两条链路能归一到同一对象（另有作用域问题，见第 5 节）。
- 风险：原生调用在受限权限下的行为需实测；重解析点与不可访问路径要按既有做法记录为读不到，而不是失败。

### 方案 B：改这四个类型的身份策略为 `native_path`（`[scope, path]`）

- 代价：**失去改名/移位的同一性**；与这四个类型自己的 `reuse_rule` 说明相冲突（它们明确写着路径复用需要代际证据）；是一次**破坏性目录变更**，需走共享改动流程并重算已写入的事实。
- 收益：用今天的素材即可成立，不需要动采集端。
- 附带：`file.acl_entry` 与 `file.alternate_data_stream` 的 `file_identity` 键改为路径形式。

### 方案 C：维持现状

- 代价：六个类型长期只有暂定身份；每次改名都表现为「一个对象消失、另一个出现」。
- 只有当「文件监控只关心固定路径、不关心改名」被确认为产品立场时，这个选项才成立——**那就应当由方案 B 明确表达出来**，而不是靠暂定身份偶然实现。

## 4. 建议

**采方案 A**，范围限定为上述三个扫描位置。理由是：这四个类型选择 `file_identity` 是模型有意为之，且 USN 插件证明该值在系统里可得；方案 B 会把一次实现便利固化成一条与类型自述相冲突的身份规则。

若采集端改动不可接受，则**采方案 B 并走共享改动流程**，不要留在方案 C——「没有决定」会让暂定身份看起来像数据质量问题，而不是一次未做的选择。

## 5. 一并记录的两处

1. **`file.watched_directory` 没有任何来源**（source-map 里没有对应行，目录备注也写着目录监控尚未接入来源）。按计划「未接入类型单独标记」，它应在对账中显式标记为未接入，而不是补一个空适配器。
2. **`hardware.volume` 的两个来源作用域不同**（`storage.volumes` 机器作用域、`usn.volumes` 盘符作用域），同一卷会成为两个实例。这与本文件的主问题独立，但同在 S14/S21 的处理范围内。
