# PCScope 状态与变化展示整改方案

日期：2026-10-13。基线：当前 `pcscope` 工作目录、模型目录 1.2.1；运行预览包为 `dist/account-records`。

整改目标是让软件直接回答三个问题：**现在是什么状态，发生了什么变化，对系统有什么影响。** 采集到的快照和日志都可以形成明确结论；正常信息直接显示状态和检查时间，只有读取失败、信息冲突或明显过期时才提示问题。名称、用途、配置、运行状态、采集状态各自表达清楚，原始依据默认折叠。

本文件保留完整整改目标，当前已开始实施；实际改动与验收状态见 [第一批实现记录](state-first-implementation.md)。逐来源、逐采集定义和逐对象类型的范围见 [全量整改清单](state-first-coverage.md)，机器可核对的同份数据见 [覆盖数据](state-first-coverage.json)。现有 RW01–RW17 不因编写方案或完成共用显示改动而结项。

## 范围与覆盖口径

| 核对对象 | 当前数量 | 口径 |
| --- | ---: | --- |
| 采集定义 | 225 | 以 `collection-catalog.json` 的完整 ID 为准，包含同一来源下的不同采集项目和前缀汇总项 |
| 采集控制条目 | 222 | 控制条目与来源不是一对一关系，不以开关个数代替功能数量 |
| 唯一来源 | 133 | 131 个实际来源声明，2 个虚拟汇总/导入来源；动态按卷来源以模板计数 |
| 来源映射 | 135 | 同一来源可有多个去向，因此不能说成 135 个独立采集项 |
| 对象类型 | 101 | 12 个类别；每类均须有名称、摘要和状态解释规则 |
| 日志通道 | 23 | 日志分类规则共 109 条，规则包含采集健康等项目，不能把每条都当作状态转换 |
| 正式采集路线 | 40 原生、91 PowerShell 兼容、2 虚拟 | 以生产路由 ownership 和包装器选择为准，存在原生函数不等于已切换生产路线 |

三个覆盖概念分别验收：

1. **方案覆盖**：每个定义、来源、类型都出现在清单中，有输出目标、整改任务和验收门槛。
2. **实现覆盖**：采集字段经过身份、含义和状态处理，能够在对应页面产生可用结果。存在适配器或能保留原始材料，不能单独算完整实现。
3. **实机覆盖**：指定系统、权限和组件环境下完成正常、变化、失败和恢复验证。静态代码审查与固定样本不替代全项实机验收。

本轮按采集代码重新生成来源目录并与对象映射核对。133 个来源均有处理去向，101 个类型均可到达；这只说明没有遗漏处理入口。此前 8 类实际对象的样本全部有可用字段，却全部没有默认摘要，证明了展示链路的共性问题；它们也不构成 225 项的新标准验收通过。2026-10-13 历史审计增加了 Security 4907 的访问记录规则解释，定义/控制/分类规则分别增加一项；没有增加日志来源或采集轮询。

## 面向用户的判断规则

| 信息 | 应得出的结果 | 例子 |
| --- | --- | --- |
| 直接状态快照 | 更新该对象的当前状态 | 平衡计划正在使用；服务运行中；安全启动已开启 |
| 明确状态变化的日志 | 更新对应状态，同时保留变化记录 | 服务已停止；账户已停用；会话已断开 |
| 操作开始、结束和结果 | 直接显示开始或完成；有明确结果再显示成功或失败 | 更新正在安装；更新安装失败；任务已完成 |
| 故障和诊断日志 | 显示发生的故障及已知影响；后续恢复信息更新故障进展 | 程序曾崩溃，随后已重新运行 |
| 配置、登记或清单 | 直接显示当前配置和清单，配置本身就是有价值的状态 | 代理已配置；软件版本；启动项已停用；存在这个驱动包 |
| 资源采样 | 显示数值、时间范围和趋势，阈值判断注明持续时长 | CPU 使用率较高，持续两分钟 |
| 采集健康 | 显示哪些信息停止更新以及影响的范围 | 防护状态暂时无法更新，保留上次结果与时间 |

正常条目不再默认堆叠“未必、仅观察到、尚不能确认”。“运行中”等当前状态指最近一次有效采集的结论，检查时间就在旁边。配置启用与运行成功应分别展示，例如“自动启动，当前已停止”；不把所有状态压成“正常/异常”。

具体示例：概览显示“当前电源计划：平衡”；计划列表显示“平衡 · 正在使用”“节能 · 未在使用”。计划名称不是状态，计划未选中也不是功能关闭。系统预设可有中文别名，自定义名称保留。原始 `Balanced`、GUID 和来源放进详情。

影响说明使用已知功能和具体变化，例如“此启动项将不会在登录时自动启动”。没有依据时不生成“会导致系统不稳定”等笼统结论；第三方、陌生名称、数字状态码也不直接等同故障或恶意行为。

## 数据处理与架构调整

沿用现有“采集器 → 原始材料 → 适配器 → 身份与投影 → 查询 → 界面”架构。新增能力放到对应层，不在前端临时执行 PowerShell、查系统或猜测对象身份。

### 统一状态读模型

每个类型声明：可读名称、少量主要属性、配置状态、运行状态、最近变化、影响说明规则、有效时间、采集更新情况。列表、详情、时间线、比较、搜索、导出使用同一套类型定义和翻译。

后端负责确定状态和值的来源；界面负责简洁表达。每个状态内部保留字段依据、发生/采样时间、接收时间、来源范围、启动/会话代际和规则版本。正常页面只展示名称、状态、必要说明和时间。仅对异常信息展示“上次为运行中，当前无法更新”等提示。

实现时可增量扩展现有查询契约，不先做整库重构。完整字段继续可查，列表每类优先显示 2–4 项；技术标识、密钥材料、命令正文、长数组和完整路径不因补摘要而全部展开。旧前后端组合要有兼容处理。

### 日志更新状态

事件转换按“通道、提供程序、事件 ID、版本/字段结构、对象类型、阶段/结果”精确匹配。每条规则声明能改变哪些字段，而不是把整个提供程序下的所有事件都当作同一种状态变化。

处理规则：

- 明确的启用、停用、启动、停止、连接、断开事件可直接更新对应字段；已有正确身份即可关联，不额外要求同步查系统。
- 操作开始只更新“进行中”，阶段结束可直接显示“已完成”；成功、失败或部分完成由明确结果字段决定，不能把结束自动写成成功。诊断故障先更新故障经历或告警进展。
- 同一字段按有效时间和来源序列处理，迟到记录进入历史，不能把较新的当前状态倒退。跨通道同秒事件没有统一序列时按明确规则处理冲突，不按数据库插入顺序瞎排。
- 快照和事件共同更新状态；更新的快照可以校正事件期间的状态。禁止“一律快照优先”或“一律日志优先”。配置开关与实际运行状态分别存储，不构成相互覆盖。
- 进程、模块、登录和任务运行按各自实例、启动周期及运行标识区分，旧进程的结束不能停止复用 PID 的新进程。
- 离线导入的旧日志默认补历史和历史区间，不覆盖现场当前状态。不能把导入时间当成事件发生时间。
- 语义已知但身份尚未绑定的事件仍显示明确活动、时间和可读对象线索。规则未知时显示“待解释事件”与来源、时间和原始线索，不编造动作；两者都保留原始记录，不污染其他对象的状态。
- 重复消费、崩溃恢复和重放必须幂等。纯采样时间改变不产生“系统发生变化”。

详细的 109 条现有分类规则全部列在采集项目清单中，逐条规定“状态转换、操作进展、故障事件、普通活动或采集健康”用途。首批转换实现后，未实现的规则继续明确标为待实现，不以全局开关宣称所有日志已状态化。

### 身份与层级

名称用于人阅读，稳定身份用于关联。更名不新建无关对象，同名不同实例不合并。修正任务目录与完整任务路径、多子项父记录绑定、网络接口范围和密钥提供程序/用户范围等问题；已完成的账户权限和组成员修复保留。

底层对象可保持细分；概览按用户任务汇总，例如“电源设置”下列当前计划、“Windows 防护”下分别列设置与运行、“操作系统”下汇总版本与重启需求。汇总展示不强行把不同范围、不同时间、不同对象的事实合成一个身份。

### 信息过期与采集异常

时效依据来源的预期采集间隔、最近成功时间、失败情况、日志断点和投影积压计算。慢变配置和瞬时进程使用不同规则。阈值进入来源配置并可测试，不在多个页面各写一套。

失败、权限不足或停止监控时保留上次有效状态及时间，标明受影响项；不能写成已关闭、已删除或已恢复。完整范围的成功空结果可以更新对应清单；局部失败不能把该范围全清空。停用采集只影响后续更新。

## 页面整改

| 页面/入口 | 必须呈现 | 验收要点 |
| --- | --- | --- |
| 系统概览 | 当前重要状态、值得关注的变化、影响和恢复进展 | 不以对象条数或“最近观察到”替代状态；可跳到对应对象/事件 |
| 系统对象列表 | 可读名称、实际状态、2–4 项主要信息、更新时间 | 类型作为辅助信息；正常状态不被身份确认文案占位 |
| 对象详情 | 当前状态、配置、最近变化、影响、必要关联 | 摘要漏字段不再导致“暂无更多信息”；原始标识和依据默认折叠 |
| 时间线 | 谁发生了什么、结果、前后变化及影响 | 与对象列表用词一致；快照变化保留区间时间，不能伪造发生秒数 |
| 比较 | 有意义的配置/状态变化 | 忽略纯观察时间、顺序抖动等噪声；解释新增、修改、移除的具体含义 |
| 采集项与健康 | 在采什么、更新时间、缺口影响、可行操作 | 未配置、未安装组件、权限不足、失败和待处理积压分别显示 |
| 搜索与导出 | 中文名称可搜索；原始名称/ID 可用于精确检索 | 展示名称与身份分离；导出保留时间、范围和依据，不把别名写回原始证据 |

“暂无更多信息”只在确实没有额外可展示内容时使用。来源未提供、读取失败、隐私隐藏、尚未支持解释四种情况要分别给出简短原因；这些提示放在相关字段，不覆盖整个对象的已知状态。

## 整改任务与交付顺序

| 任务 | 优先级与责任范围 | 交付物与完成门槛 |
| --- | --- | --- |
| SP01 摘要与状态读模型 | P0；查询与界面、对象目录 | 101 类展示规则；类型化摘要选择；8 类空摘要反例修复；列表/详情依据一致 |
| SP02 事件更新状态 | P0；事件适配、基础数据 | 109 条分类逐项登记转换能力；首批状态转换、顺序/重复/导入隔离/恢复处理；未实现项可列举 |
| SP03 字段含义与枚举 | P0/P1；类型适配、目录 | 防护设置和运行拆分；有来源依据的枚举/单位/时间解释；原始已有但未承接的字段逐项处理 |
| SP04 身份与关联 | P0；基础数据、类型适配 | 任务完整路径、多子项、范围/会话隔离的反例与修复；历史记录可重放核对，不改原始材料 |
| SP05 名称与跨页面文案 | P1；查询与界面 | 中文预设名、保留自定义名；状态中性类型名；所有入口共用解释；缺名有用途而非一片“未确认” |
| SP06 采集健康与时效 | P1；采集调度、查询与界面 | 逐来源时效、异常影响、恢复显示；采集失败不抹掉上次状态；内部健康来源有入口 |
| SP07 原生采集与性能 | P0/P1；平台采集、存储、调度 | 91 条兼容路线逐项迁移/验收；同源单一生产者；超时、退避、取消、防自采集、去噪、积压和容量治理 |
| SP08 SIHost 模块文件跟踪 | P0；原生模块采集、存储、查询 | 运行实例→加载模块→磁盘文件→变更→风险与恢复展示；区分第三方、未验证签名、文件变化和加载失败 |
| SP09 验收与迁移发布 | P0 贯穿；各线负责本项，集成负责对账 | 225 定义/133 来源/101 类型/109 日志规则无遗漏；场景及环境矩阵；历史回放、性能、权限流程和打包验证 |

实施顺序：

1. **先打通已有明确状态**：SP01 与 SP05 共用规则，先处理电源、服务、可选功能、安全启动等已具备字段的来源；SP03 同时隔离防护等含义冲突，不把有问题的值一起放出。
2. **修正身份和事件更新链路**：SP04 与 SP02 并行，先以有稳定身份的服务、任务、账户、进程和会话建立状态转换闭环，再扩到各来源。身份缺失不阻止事件本身可读展示。
3. **补完整类型规则和真实字段缺口**：按全量清单完成剩余来源/类型，修正同源多项目、未知枚举、复合材料和汇总视图。
4. **完成健康、SIHost、原生与长期性能**：SP06–SP08 与前述工作持续集成；这些涉及既有 RW 任务，不能仅凭文案更新结项。
5. **全项验收和发布**：SP09 按已固定的范围逐项签收，完成原生包与桌面匹配检查、权限升降级、历史回放及恢复。

以上是依赖顺序，未给未经测量的工期承诺。每个任务以可验证的交付物结项，不以“已增加词典”或“已有适配器”代替完整功能。

## 原生、权限与性能约束

已有系统接口能够完成的采集放到后台原生路线。PowerShell 兼容项按全量清单逐个迁移，切换前验证正常、空、失败、取消、范围和字段等价；原生失败保持可读错误和上次状态，不自动启动脚本回退。

一个来源同一时间只有一个采集任务；事件触发按对象合并、去重和冷却，不允许日志变化再次无限触发自身采集。子进程有超时和并发预算，失败指数退避，UI 刷新不得启动新一轮采集。数据库、缓存、日志、临时目录和自身辅助进程的活动不得形成反馈循环。

权限由现有普通/增强后台承接。界面说明具体受影响能力，管理员也不自动等于所有信息完整。用户范围信息保持正确用户和会话身份；后台独立运行、登录前运行和机器服务部署的能力另按 RW14 验收。此次编写方案不触发 UAC，不更改审计设置。

正式程序的运行和权限获取不依赖 Codex。开发环境的权限仅用于开发验收；发布后的桌面与后台通过产品自身的 IPC、Windows 授权和启动流程工作。普通桌面不因后台增强采集而整体提升权限，取消授权后有明确可用范围和可恢复操作。

性能验收拟定门槛：固定机器和数据规模后，50 行常用列表 P95 不高于 2 秒、常用详情 P95 不高于 1 秒、轻量状态/设置 P95 不高于 200 毫秒；6 秒超时是保护上限，不是合格目标。必须记录硬件、数据库规模、冷暖缓存和并发采集条件。24 小时压力运行中队列不能持续无界增长，存储受配置配额约束；记录 CPU、内存、子进程次数、磁盘增长和积压恢复时间。当前实测不足以宣称这些目标均已达到。

## SIHost 的具体完成标准

保留用户已选定方案：从运行中的 SIHost 实例发现模块，再跟踪这些模块对应文件的存在、内容、大小、版本、签名、权限和身份变化。默认呈现“桌面组件文件已更改/无法读取/文件缺失”等状态，显示关联运行实例及已确认影响或具体风险。

验收须逐一覆盖同路径替换、重命名、删除重建、进程重启、账户/会话变化、权限拒绝、读取中变化、超限文件及第三方签名未知。文件变化发生后可安排有预算的复核；不能立即断言内存模块已损坏。后续出现加载失败或崩溃日志时关联时间和对象，明确显示已发生的失败；相关性与已确认根因分别处理。

监控覆盖从成功发现该模块开始。尚未运行、从未成功加载的候选依赖、登录前阶段以及内容语义损坏未被该方案全部覆盖，见 RW14–RW17 和全量缺口清单。此边界放在监控范围说明中，不反复打断每条正常模块状态。

## 验收与历史数据处理

每个采集定义至少登记：正常输出、有意义的变化、正常无变化、空结果/不适用、关闭采集、读取失败与恢复；按其能力补充权限、敏感值、未知枚举、重复、乱序、跨范围和重启场景。无对应组件的环境明确记为“该环境未验收”，使用夹具验证不冒充实机通过。

每项还需形成实际字段清单，逐字段登记“采集值 → 模型字段/事件字段 → 用户表达或保留原始材料的原因 → 验收样本”。当前来源目录的 `fields_enumeration` 仍使用待枚举占位，本轮按来源和类型覆盖不等于已完成所有原始属性的逐字段验收；SP03、SP09 负责补齐并对账，不能以来源存在代替字段完整。

| 验收层 | 必须通过的检查 |
| --- | --- |
| 范围对账 | 224 个定义、133 个来源、101 个类型、108 条日志规则无缺项、重复或无任务项；两条前缀定义和内部 USN 状态有明确归属 |
| 语义 | 当前状态、配置、事件结果、记录生命周期和采集健康不串义；明确日志可直接更新状态；未知值不误判 |
| 身份 | 同目录不同任务、同名跨范围密钥、同父记录多子项、PID 复用、重启/账户/会话变化彼此隔离 |
| UI | 正常、异常、过期、恢复、缺名、同名、长名均可读；列表/详情/时间线/比较/搜索/导出一致 |
| 时序 | 新旧快照、迟到事件、同秒冲突、重复、离线导入、断点恢复、旧规则重放不污染当前状态 |
| 环境 | Windows 10 LTSC x64 与 Windows 11 x64；普通/增强权限；相关组件已安装/缺失/停用；当前用户与其他会话边界 |
| 安全与性能 | 敏感值仍受保护；不启动无限脚本循环；索引和分页有界；大库、持续采集、退出恢复通过 |

既有原始材料保留。新增状态投影以规则版本记录，先在隔离副本/新投影中回放并核对，再切换读取；大库分批、可恢复、可取消，避免全量同步重建卡住界面。旧错误身份或误归类要有迁移规则和对照，不用人工改写原始日志。缺少过去的材料时保留历史缺口，不补造状态。

完成标准是：用户能从主界面读出当前状态和最近变化；每个来源有自己的明确用途，确有缺口的项目能单独列出；全部适用采集项有新标准验收记录。状态展示合格与采集范围完整分别结项。
