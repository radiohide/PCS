# 事实、动作、时间与清理语义决策表（R04 冻结）

日期：2026-09-12。状态：**已冻结**（契约版本 1）。代码：`crates/contracts/src/semantics.rs`；样例：`crates/contracts/examples/semantics-contract.rs`。

依据：[并行开发前置条件与准入方案](parallel-readiness.md) R04；[对象监控模型设计](../object-model.md) 第 5–8 节。

R04 是 S07、S08 的**提前实现**：本步冻结判定规则并给出固定预期，**当前值选择、清理与故障恢复的实际实现仍由 S07/S08 完成**。

本文件是这些语义的唯一出处。任何工作线不得自行定义枚举取值或缺失值的含义；枚举本身来自 `model/catalog.json`（值状态、推导方式、时间精度、结果语义）与本模块。

## 1. 时间

### 1.1 编码

| 决定 | 规则 | 被否方案与理由 |
| --- | --- | --- |
| 存储形式 | **UTC，RFC 3339，小数秒固定 3 位**，如 `2026-09-11T09:30:00.123Z` | 变长小数秒被否：`…:00Z` 与 `…:00.500Z` 按文本比较会把后者排在前面，而它其实更晚。存储层用文本范围查询，必须保证文本序等于时间序 |
| 时区 | 只接受 `Z` 结尾；带偏移的时间**拒绝**，由采集层转换后再入库 | 在契约层做偏移换算是日期运算，容易出错且需要额外依赖；采集器已经统一用 `ToUniversalTime().ToString('o')` |
| 小数秒 | 超出 3 位**截断**，不四舍五入 | 四舍五入会让存储值晚于来源实际声明的时间 |
| 实际格式 | 采集器产出 7 位小数秒（PowerShell `o` 格式），入库时间由 SQLite `strftime` 产出 3 位；两者都能规范化，并有测试覆盖 | — |

### 1.2 三个时间不合并

`source_time`（来源声明的事实时间）、`observed_at`（PCScope 看到它的时间）、`ingested_at`（写库时间）始终分开保存。缺发生时间时**不伪造**，退回观察时间并标注。

### 1.3 排序锚点

每种排序读哪个时间，明确如下：

| 排序 | 锚点 | 说明 |
| --- | --- | --- |
| 按发生 | 精确：`occurred_at`；区间：`interval_until`；仅观察：`observed_at` | 区间用**上界**：那是变化确定已生效的最早时刻。用下界会声称变化在它被观察到之前就已发生 |
| 按观察 | `observed_at` | 永远是真实时间，不派生 |
| 按入库 | `ingested_at` | — |

锚点附带 `derived` 标志。**派生锚点必须在界面上可见**：把观察时间显示在「发生时间」列里，等于宣称了我们并不具备的精度。

同一时间的稳定第二排序键：记录用 `seq`，对象用 `instance_id`。**不使用可能重复的字段作唯一排序依据。**

## 2. 缺失与遮罩

### 2.1 六种缺失状态的区别

| 状态 | 含义 | 何时使用 |
| --- | --- | --- |
| `not_provided` | 来源结构里没有该字段 | 来源压根不提供 |
| `unreadable` | 字段存在但读取失败 | 权限不足、读取被拒 |
| `not_applicable` | 该字段对本实例没有意义 | 例如电池字段之于台式机 |
| `conflicting` | 多来源给出无法消解的不同值 | 见第 3 节 |
| `masked` | 值受保护，默认显示遮罩 | 见 2.2 |
| `evidence_pruned` | 值曾采集到，支撑证据已按保留策略清理 | 见第 5 节 |

显示缺失时按信息量排序取最具体的一个：`evidence_pruned` > `unreadable` > `conflicting` > `not_provided` > `not_applicable`。这个排序**只决定显示哪一个缺失**，绝不把缺失变成值。

### 2.2 遮罩是显示转换，不是存储状态

**决定：**

- 受保护字段的**真实值**入库（按既有 DPAPI 加密策略静态加密），`masked` 只表示「默认显示为遮罩」；
- 显示遮罩 `******` **在任何情况下都不得作为持久值**；
- 遮罩字符串**不参与身份匹配，也不参与变化比较**；
- 来源若把遮罩当作值提交，整条观察被**拒绝**（`CurrentValue::Refused`），而不是把它当成一个值存下来。

被否方案：把 `masked` 当作「值未知」的一种。理由——那样会把「我们有意不显示」和「我们没有这个值」混为一谈，而两者的界面含义与后续处理完全不同。

## 3. 当前值选择

**排序依据是生效时间，不是入库顺序。** 生效时间取 `source_time`，缺失时取 `observed_at`。

| 情形 | 结论 |
| --- | --- |
| 生效时间不同 | 取最新者。**旧事件晚到不会回退当前值**——它按生效时间排在后面，永远不会被选中 |
| 生效时间相同、值相同 | 取该值，并引用**全部**同意的来源，而不是只记第一个 |
| 生效时间相同、值不同 | 判为**冲突**，保留全部候选值及各来源 |
| 无任何值 | 按 2.1 的次序报告最具体的缺失 |
| 值等于遮罩哨兵 | 拒绝 |

**冲突是默认结果，不是异常。** 只有在目录中显式声明了来源优先级时，同一生效时间上的分歧才可被消解；当前目录**没有声明任何优先级**，因此分歧一律保留为冲突。宁可显示冲突，也不静默地替用户选一个。

被否方案：按「采集器/插件可信度」隐式排序。理由——那是没有依据的偏好，且会让同一份数据在不同版本间给出不同结论。

## 4. 动作

### 4.1 配置变化与运行状态变化分开

字段变化产生的动作**由字段性质决定，调用方无法选择更强的措辞**：

| 字段性质 | 动作 | 目录中的性质 |
| --- | --- | --- |
| 配置 | `observed.configuration_changed` | `snapshot_change` |
| 状态 | `observed.state_changed` | `state_change` |
| 身份 | 无 | 身份变化意味着**另一个实例**，由身份层处理，不是一条变化动作 |

**这直接保证了「任务下次运行时间变化不会直接被解释为人工修改」**：`next_run` 在目录中是状态字段，它只能产生 `observed.state_changed`，而该动作在目录中的性质是 `state_change`，不是 `source_recorded`。任何字段变化都无法产生来源记录类的动作——这一条由测试对目录校验，不是靠约定。

### 4.2 归并

两条记录判为同一次动作，需**同时**满足：

1. 目标对象相同（类型、作用域、身份字段与缺失键全部一致）；
2. 动作类型相同；
3. **阶段相同**——开始与结束是两个阶段，必须分别保留，不得去重成一条成功事件；
4. 时间精度相同，且发生时间（精确）或区间（区间）完全一致。

**时间接近永不作为归并依据。** 相差一秒也判为两次动作。

**观察时间-only 的动作永不归并**：它没有可比较的发生时间。

未归属的动作不参与归并：目标本身就是未定的，无从断定两条记录指向同一次动作。

多份证据支持同一次动作时，归并后保留**全部**证据引用，而不是只留最先到达的一份。

## 5. 证据清理后的引用

| 情形 | 结论 |
| --- | --- |
| 引用可解析 | 返回可用引用 |
| 证据已被保留策略清理 | 返回 `Pruned`，带**清理时间**与**保留起点**，绝不返回空值或悬空指针 |
| 当前结论 | 保留：当前事实有自己的值与观察时间，不因证据被清理而消失 |
| 历史版本 | 支撑证据已被清理且无其他支撑的历史版本不再保留（清理粒度属 S08） |

## 6. 完整快照的范围：何时可以判「未发现」

必须**同时**满足四项，任一不满足则明确报告原因，而不是显示为对象消失：

| 条件 | 不满足时的结论 |
| --- | --- |
| 采集项处于启用状态 | 停用期间的缺失不构成未发现 |
| 本轮采集成功 | 读取失败不能当作未发现 |
| 本轮快照完整 | 不完整快照中的缺失不能当作未发现 |
| 实例所在范围被本轮采集覆盖 | 范围变化不是对象消失 |

四项由 `absence_eligible` 分别报告，界面据此说明「为什么不能下结论」。即使四项都满足，结论也只是**未发现**，不是删除——删除需要一个来源**明确声明**（见身份契约第 7 节）。

## 7. 未决项（阻塞 S07/S08 的，必须在使用前解决）

1. **来源优先级尚未声明。** 当前所有同生效时间的分歧都成为冲突。若实际使用中冲突过多、需要在特定字段上指定权威来源，必须先在目录中显式声明优先级规则及其适用范围——**不得由实现方隐式决定**。
2. **`not_applicable` 的产生方式未定。** 是由类型声明「本实例不适用该字段」，还是由适配器在识别出实例形态后判定？在 S09–S20 只读类型适配前无法确定。
3. **历史版本的清理粒度未定。** 「支撑证据已被清理且无其他支撑的历史版本不再保留」中的「其他支撑」如何界定，属 S08 的清理算法。
4. **区间动作的展示锚点**已定为上界，但若某些来源能给出更紧的区间，是否需要按来源收紧区间，待 S09–S20 观察真实数据后再定。
5. **未实现文件内容版本**，因此「文件变化」目前只能表达为元数据与 USN 原因位，不能表达内容差异（既有能力限制，非本步新增）。
