# 0007 覆盖视图带上该来源的投影进度

| 字段 | 内容 |
| --- | --- |
| 共享入口 | 公共契约（`crates/contracts/src/query.rs`） |
| 整合责任人 | 基础数据线 |
| 提出工作线 | 查询与界面线（S25 实施采集健康页时发现） |
| 变更类型 | **兼容性新增**（`CoverageView` 增加一个带 `#[serde(default)]` 的字段） |
| 影响的工作线 | 查询与界面线（多一个可展示字段）、迁移验证线（固定响应集重新生成） |

## 问题

计划第 8 节要求采集健康页「统一来源范围、读取能力、补采与对象投影进度；**采集失败和解析失败分开**」。

前两项 `CoverageView` 有；后两项没有。而 S08 的覆盖报告**早就返回了**投影计数（`projection: {pending, failed, done}`）——也就是说**存储层返回的形状超出了契约声明的形状**。这不是「契约少了字段」，是「实现自己长出了一个字段而契约不知道」。

前端渲染器声明它读取这三条路径时，`check-model-view.cjs` 立刻报了出来：这三条路径在固定响应集中不存在。检查抓到的是**实现与契约的分歧**，不是拼写错误。

## 旧结构 / 新结构

| | 旧 | 新 |
| --- | --- | --- |
| `CoverageView` | 来源、范围、开关、最近结果、最近成功/尝试、历史完整度、说明 | 同上 + `projection: ProjectionCounts` |
| 投影计数位置 | 只在存储层的 JSON 里，契约未声明 | 契约声明（`ProjectionCounts { pending, failed, done }`） |

**为什么放在覆盖视图里而不是另开一条查询**：健康页要「采集失败和解析失败分开」，而这两个数**必须并排才有意义**——「来源被拒绝」和「来源读了但没人看得懂」是两种不同的处置。分成两条查询让页面自己去对应来源合并，既多一次往返，也把「它们属于同一个来源」这件事交给前端猜。

## 兼容性

纯新增且带 `#[serde(default)]`：既有消费者（含 R09 的替身）不加改动即可反序列化，缺少该字段时得到全零。R09 替身确实构造了该结构，已补上并注明它同步投影、没有队列，因此 0/0/0 是它**实际的值**而不是占位。
