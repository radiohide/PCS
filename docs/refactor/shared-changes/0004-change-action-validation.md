# 0004 适配器校验拒绝单侧的变化动作与无跨度的区间

| 字段 | 内容 |
| --- | --- |
| 共享入口 | 公共契约（`crates/contracts/src/adapter.rs` 的 `validate`） |
| 整合责任人 | 基础数据线 |
| 提出工作线 | 基础数据线（R09 收尾复验中发现，与共享改动 0003 同源） |
| 变更类型 | **破坏性变更**（`validate` 会拒绝此前判为合法的候选） |
| 影响的工作线 | 类型适配线（S09–S20 的每一个适配器）、迁移验证线；查询与界面线不直接受影响 |

## 问题

共享改动 0003 修掉了替身投影产出的幻影变化动作。修完之后发现：**那种动作走 `validate` 是完全合法的**。

`validate` 当时对动作的规则是：

- 区间动作 → 必须有两个边界，且不得声称精确时间；
- `before` / `after` **只要有一侧存在** → 必须写 `field_id`。

缺两条：

1. **没有「两侧必须都存在」。** `before: Some(true), after: None` 判为合法——即使 R04 的结论是「缺失不是值」。一个值为空的变化动作宣称某个值出现或消失了，而没有任何来源观察到这件事。
2. **没有「区间必须有跨度」。** `09:00:00Z → 09:00:00Z` 判为合法——即使 R04 §3 已经规定生效时间相同的两条观察是「取该值并引用全部来源」或「冲突」，都不是随时间的变化。零长度区间宣称变化发生在某个时刻与它自己之间。

后果比替身里的那四条动作严重得多：**S09–S20 的真实适配器走的正是这个校验器**。同一个读法会在真实来源上重演，而那时不再有演练检查兜着——R09 新增的 `check-drill.cjs` 只检查演练输出。

## 旧结构 / 新结构

| 规则 | 旧 | 新 |
| --- | --- | --- |
| 变化动作的两侧 | 任一侧存在即要求 `field_id`；两侧不齐不影响 | 任一侧存在即要求 `field_id`，**且两侧都必须存在** |
| 区间动作的跨度 | 只要求两个边界存在且未声称精确时间 | 边界先规范化，再要求 `from < until`；边界必须能规范化为 UTC RFC 3339 |

规范化一步是必需的，不是额外严格：`compare_canonical` 只比较**已规范化**的文本，直接比原始字符串会让 `…09:00:00Z` 与 `…09:00:00.000Z` 这两个同一时刻被当成两个不同瞬间，恰好从零长度规则里溜过去。同理，无法解析为时间的边界不能用来界定任何区间。

## 兼容性

破坏性：若某适配器此前产生过单侧 `before`/`after` 或零长度区间，其候选现在会被拒绝并给出具体位置（`actions[i].before_after` / `actions[i].interval`）。

本仓库内**没有任何适配器依赖旧行为**：全部 45 项 `pcscope-contracts` 测试、6 个契约示例、17 个检查脚本在改动后一次通过，`model/drill-output.json` 逐字节未变。参照适配器与 `fixtures/contract/` 的用例都产生两侧齐备、跨度非零的变化动作。

## 数据迁移

不需要。候选是适配器的输出、不是持久事实；S09 尚未接线，没有已入库的动作需要重算。

## 本次未覆盖的边界

`validate` 校验的是 **`ActionCandidate`**，即适配器的输出。而变化动作的最终产生者是 S07 的投影，它输出 `ActionView`，**不经过 `validate`**。R09 的 `check-drill.cjs` 覆盖的是替身投影，S07 替换替身时需要决定真实投影的输出走什么校验——本次没有替它决定。
