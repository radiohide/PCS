# 0.2.22 首次采集进入时间线

## 用户看到的变化

首次采集到的对象进入时间线，卡片显示“首次记录”，按原采集时间归入既有时间组，支持类别筛选、折叠、自动加载和详情。已有的首次采集历史也会补齐，后续新采集范围自动接入。

原有新增、再次出现、消失及属性变化继续保留各自含义。初始清单没有创建或安装时间时，仅使用实际采集时间。打开“查看当前状态”仍读取对象当前状态；补齐历史不会让已消失的设备、进程或模块恢复为当前存在。

## 后台处理

- 使用已有 `baseline.observed` 原始记录，沿 `record_search_kind(kind,seq)` 索引顺序读取，不扫描全部日志或在页面请求中解析原始清单。
- 复用现有投影线程：正常采集投影清空后，最多每秒准备一批 32 条；批内 40 ms 软时间预算、2 MiB 总材料预算、单条 1 MiB 上限。单次数据库调用仍可能超过软预算。
- 入队、证据引用及游标在同一事务提交。失败退避，最长 60 秒；重启从持久游标恢复，已完成时只作索引尾部检查，不反复写空进度。
- 沿原来源、采集项、原生记录编号、范围、对象类型和首次观察时间绑定唯一对象；一个初始父项中的成员等子对象分别进入时间线。多来源、分片和重放对同一对象只保留一次首次记录。
- 继续使用 `observed.first_seen`，以 `snapshot_presence.baseline=true` 标明初始清单，保持原始状态的小摘要。已有动作定义、数据库结构、展示版本及旧展示缓存均不重建。
- 已停用采集项的既有历史仍可补齐。无对象读数、无适配器、无法唯一绑定、无有效完整观察、材料已清理或超出材料预算的项目不生成猜测记录；原始记录不改写。
- 自动维护状态包含本批检查、入队、跳过、游标和耗时，供诊断使用；正常补齐不增加每张卡片的解释提示。

## 验证

- 208 项存储测试、28 项后台测试通过。
- 新增测试验证原始采集时间、无虚构发生区间、已有消失状态不回退、两条初始记录跨批恢复、重复运行不增加记录、原始材料不变。
- 验证父对象及两个成员分别生成记录，新增来源分片不会重复生成。
- 在 20,000 条无关事件中使用 SQLite 指令预算验证索引路径；原材料在入队后消失时，该项结束为失败，后续有效项仍继续。
- 最后补充停用采集项后仍补齐其历史的断言，相关首次采集测试再次执行。
- 45 项真实前端交互场景通过，新增“首次记录”卡片打开当前对象详情；全部目录对象类型的首次采集标签和简洁措辞检查通过。
- 正式库只读统计约 13,858 条 `baseline.observed` 原始记录。这不是承诺生成相同数量的卡片：同一对象多来源会合并，父项可展开多个子对象。

构建使用固定 `dist/dev` 与桌面 debug 入口。

## 正式验收与 0.2.23 调度修正

2026-10-20，经用户 UAC 授权启用 0.2.22 增强后台。正式库已生成首次采集动作，原采集时间保留；真实 WebView2 中选择已有类别／类型／全部时间筛选，显示“首次记录”，按需原始详情及当前对象详情均可打开。

- 一个单记录类型的真实时间线渲染完成约 65 ms，原时间为 2026-10-15，未使用更新当天的时间。
- 该对象详情第一次读取发生超时，随后同一对象直接重试约 514 ms 成功，完整交互重跑通过；不把此验收描述成所有查询从未超时。
- 补齐过程抽查硬件全部时间 182 ms、未筛选时间线 121 ms。此时已生成 574 条初始动作；补齐尚未完成，不将原始记录数量当作生成动作数量。

生产验收同时发现：后台长时间保持待处理队列，0.2.22 的“队列为空才准备初始记录”条件会延迟补齐。0.2.23 改为正常投影批次成功后按既定频率准备，不再要求全局空闲。原始快照与对应记录一起提交，补齐工作追加到同一先进先出队列，仍确保原始对象观察先处理。

0.2.23 的 28 项后台测试、4 项首次采集存储测试通过；新增明确验证“原始观察仍在排队时追加初始记录，按顺序各处理一条即可完成”。已有补齐游标与展示版本保留。修正版增强后台尚待新的 Windows 授权启用。
