## 2. 缺陷一：导出脚本看不见写在变量里的载荷

**现象。** 有些采集项把载荷先建在变量里，再交给 `Item`：

```powershell
$data=@{path=...;target=...;arguments=...}
Item $key $data
```

`Item` 调用里没有哈希表字面量，因此只从 `Item` 内联哈希表取字段的导出脚本**看不到这些字段**，`target/collector-schema.json` 里这些采集项的 `fields` 为空，文档的字段表随之变空。这与 `S32-switch.md` 第 8 节观察到的 `"data": {}` 是同一件事。

**修复。** 先收集块内「变量 ← 含哈希表的赋值」，再在 `Item` 分支解析变量实参；同时把嵌套哈希表一并收进（载荷可能内嵌子记录）。一个易错点记在这里：`$data=@{...}` 解析为外层 `CommandExpressionAst` 包着哈希表，**直接对它做 `-is [HashtableAst]` 永远不匹配**，必须在其右值内部 `FindAll`。另一处：同一变量可能被赋值多次（`desktop.ps1` 的分支写法），按 `+=` 合而不是覆盖，才与文档「跨分支字段集合」的语义一致。

**实测（新旧脚本各跑一次，逐行对比）。** 99 条声明两侧完全一致，只有 4 条字段集变化，**全部是新增，零删除**：

| 声明 | 位置 | 新增字段数 |
| --- | --- | --- |
| `pcscope.desktop.shortcuts` | `domains/desktop.ps1:8` | +13 |
| `pcscope.software.portable` | `domains/scoped.ps1:76` | +11 |
| `pcscope.files.metadata-security` | `domains/scoped.ps1:75` | +8 |
| `pcscope.startup.logon` | `collect-system.ps1:159` | +6 |
| | **合计** | **+38 / −0** |

`pcscope.desktop.shortcuts` 新增后恰为 13 个字段（arguments、attributes、basis、collection、description、hotkey、icon、path、reason、reparse_target_followed、target、window_style、working_directory），与已提交文档里列出的那 13 个逐项相同——说明已提交文档记的是**当时正确**的字段集，而工具链此后丢失了这个能力。修复后 `"data": {}` 由有变无（当前文档 0 处）。

## 3. 缺陷二：事件示例依赖未提交的本机样本，缺了会静默变薄

**现象。** 重生成后，§5 各事件示例的 `"fields"` 变成 `{}`，文档比已提交版本少掉大量 Windows 事件字段名。

**成因。** 事件字段名**无法从源码推出**——只有真实事件能说明某个 `(source, provider, event_id)` 带哪些字段。生成器因此读 `target/event-audit.json`（`build-data-display-reference.cjs:49`），该文件由 `crates/storage/examples/event-audit.rs` 只读审查真实库得到，**按设计不提交**（`docs/event-classification.md:39`：审查样本含本机元数据，仅留在被忽略的 `target/`）。

关键在于原来写的是：

```js
const audit=fs.existsSync(fixturePath)?JSON.parse(...):[];
```

样本不在时**不报错**，只是让每条事件示例渲染成空字段——产出**更薄但看起来完整**的文档。这正是 S27 第 1 节和 S32 第 4.1 节反复记过的那类失败：干净退出、产出为零或残缺，而没有任何信号。

**修复。** 缺样本改为直接失败（生成器原本就 `require` 了 `assert` 并在文件末尾用它做内容校验，这里沿用同一风格），并把重建步骤在文档里补全为三步。实测：

| 情形 | 退出码 | stdout | 文档文件 |
| --- | --- | --- | --- |
| 样本在位 | 0 | 统计 JSON | 重写为 17,413 行 |
| 样本移除 | **1** | **0 字节** | **逐字节未变**（哈希一致） |

失败信息即所要的命令：`cargo run -p pcscope-storage --example event-audit -- <database> > target/event-audit.json`。**失败发生在写文件之前**，不会留下半成品。

## 4. 缺陷三：概览页的计数被旧计数覆盖

**现象。** 概览页的计数块由对象模型渲染——对象类别、对象类型、当前对象、来源记录、动作、证据、来源（`apps/desktop/ui/model-view.js:220`）。而「载入最新」的处理里写的是：

```js
const counters=content.querySelector('.stats');if(counters)counters.outerHTML=stats();
```

`stats()`（`app.js:14`）读的是 `state.status.counts`，即**旧的 `records` / `objects` / `snapshots` 计数**。而概览页的第一个 `.stats` 正是模型计数块——于是点一下「载入最新」，模型计数被旧计数顶掉。这就是「正式页面依赖旧对象分类」的实例：不是还有旧代码存在，而是**一个已经走新模型的页面被旧计数改写**。

**修复。** 旧计数块加一个类 `stats-legacy`（`.stats` 仍在，样式不变），刷新路径改为只选 `.stats-legacy`。仍读旧计数的页面行为不变；概览页保住自己的计数——它自己的渲染器随后本来就会刷新一次。

**为何过去没被检查脚本发现。** `scripts/check-front-refresh.cjs` 本来就跑这段处理，但把 `content.querySelector` 打桩成恒返回 `null`，那个替换分支**从未被执行过**。现在该脚本记录处理过程问过哪些选择器，并断言：必须选中 `.stats-legacy`，且不得出现裸 `.stats`。两个方向都验过：

| 情形 | 结果 |
| --- | --- |
| 已修复 | 通过 |
| 把选择器改回 `.stats` | **失败**，报 `refresh path must target the legacy counter block` |

### 8.6 单向门的复现：只在临时夹具上，正本未被打开

计划把「单向门复现」列为验证第 2 项。本轮在临时夹具上复现了**两个方向**，夹具写在 `target/verify-oneway/`（按仓库约定，测试产物只落在 `target/` 下），**没有碰任何真实库**：

| 方向 | 夹具 | 结果 |
| --- | --- | --- |
| 旧库被**就地升级** | 手工建的 v4 库（含 `retention_mode`/`quota_bytes`/`pruned_units` 三行设置） | 当前构建打开后 `user_version` **4 → 8**、30 张表、退出码 **0**、`timeline` 返回 `[]` |
| 更新的库被**拒绝** | 同一夹具改成 `user_version=9` | 退出码 **1**、stdout **0 字节**、stderr 恰为 `Error: database schema version 9 is newer than this application (8); upgrade the application`、文件 **sha256 未变**、**未生成 `-wal`/`-shm`**——拒绝发生在任何写入之前 |

**这一项真正要确认的是第一行**：删除 `migrate.rs` 有可能连带删掉 schema 升级路径。实测没有——**升级在 `Store::open` 的版本阶梯里（`crates/storage/src/lib.rs:100-182`），不在被删的 `migrate.rs` 里**（后者做的是「旧数据 → 对象模型」的数据迁移，两件事同名不同物）。拒绝的闸门在 `lib.rs:82-88`，`open_reader` 的 `:213-215` 同样拒绝，故只读路径亦不会把新结构当旧结构读。

与 S32 第 5 节第三项的关系：那里记的 55 字节 stderr 是 **schema-4 时代二进制的措辞**（`Error: database version is newer than this application`），当前构建的措辞带版本号。**同一条门，措辞不同**，两处不矛盾。

**正本没有被打开。** 复现后复核正本 `%LOCALAPPDATA%\local.pcscope.desktop\history.db`：`user_version` 仍为 **4**、主文件 mtime 仍为归档前的 **2026-09-11 06:39**、`-wal` **0 字节**。计划验证第 2 项原本写成「新构建首次打开正本后 `user_version` 变 8」，**本轮没有那样做**：那一步不可逆，而计划 §19 的处置是「先留档、旧行留在原地、正式切换不做」。因此本节复现的是**机制**，不是对正本的操作；正式切换仍属 S32 未完成的范围。

**一处夹具陷阱，记下来备查**：第一版夹具只有一张空的 `settings` 表。`Store::open` 的升级**成功了**（v4 → 8，模型表齐备），但紧接着 `maintain_capacity` 读不到 `retention_mode` 而报 `Query returned no rows`、退出码 1。真实 v4 库一定有该设置行（S02/S04 已记），补上后即退出 0。**若日后有人拿一个缺保留设置的库去开，看到的会是这个错，而不是版本问题。**
