## 1. 对账不是数数

计划写明「**不能用对象数量相等代替对账**」，因此报告里没有任何一个总数被当作一致性的证据。每一节回答的都是**关于单份输入的问题**：

| 节 | 回答什么 |
| --- | --- |
| `inputs` | 每个来源各有多少份材料、其中已投影/失败/待办/**完全没有处理状态**各多少 |
| `failures` | 失败按来源与**原因**分组——计划问的是「每条失败是否已修复或明确不可恢复」，那要逐条看原因 |
| `unprocessed` | 有材料但**连一条处理状态都没有**——这是"没决定"而不是"成功"，只统计成功的报告会把它显示成不存在 |
| `field_trace` | 当前字段是否都有还存在的证据支撑；**当前值是否比模型已持有的证据更旧**；有无悬空引用 |
| `identity` | 各身份状态计数、多来源实例清单、暂定键的数量 |
| `watermarks` | 证据水位与队列水位是否齐平、是否还有待办 |

## 2. 验收条件对照

| 计划验收 | 结果 |
| --- | --- |
| 每份保留输入都有处理状态 | 通过：`every_input_gets_a_status_and_the_verdict_says_when_one_has_none`——未投影前该输入显示为待办且判定为 `incomplete`，投影后显示为已处理 |
| 当前关键字段与最新可靠证据一致 | 通过：`facts_behind_their_evidence`——有值字段引用了比它自身更新的证据即计为不一致；干净库上为 0，并被纳入判定 |
| 全部解析失败已修复或明确为输入不可恢复 | **部分通过**：失败按来源与原因逐条列出（`failures_are_reported_with_the_reason_they_failed`，断言原因含 `no adapter`）。「是否可恢复」的**判定权不在工具**——未接入来源的失败在 S21 例外表里已明确为「未有适配器前不可处理」，其余需逐来源判断。见第 3 节第 1 项 |
| 已确认身份无错误合并 | **部分通过**：键级不可能碰撞（`object_instances` 上有唯一约束，S04 已强制）；**语义上的错误合并无法由工具判定**，因此多来源实例被**列出供人工抽样**而不是被判定。工具能看见两个来源在同一个实例上相遇，看不见它们是否本应相遇 |
| 增量新增记录在最终水位前处理完毕 | 通过：`the_watermarks_say_whether_everything_that_arrived_was_dealt_with`——投影后齐平且 `settled`，新到一批后立即变为未齐平 |

## 3. 遗留问题

1. **「可恢复性」是人的判断，工具只提供依据。** 报告给出每条失败的原因和规模；把「不可恢复」定为结论需要逐来源看输入，而这件事需要真实旧库才有意义。S21 的例外表已经对 7 个来源给出了结论（其中 `apps.dotnet-runtimes` 是「未实现」而非「不可恢复」——**这两种在报告里目前不加区分**，都表现为队列失败）。要不要在报告里区分「适配器缺失」与「材料损坏」，属后续改进。
2. **未在一致性副本上跑过完整迁移。** 计划要求「在一致性副本上完整迁移」后再对账；本步交付的是对账工具与其在内存库上的验证。**真实旧库副本上的完整对账属 S31**，那里才有真实的规模、异常材料与清理边界。
3. **多来源实例的抽样清单上限 50 条。** 真实库上可能远多于此，报告会截断——截断时未在输出里注明「还有更多」。这是一个已知的呈现缺陷，属 S31 完善。
4. **S27 留下的两条仍未处理**：被清理输入的边界记录、事件记录因缺世代未迁移。两者都要在**真实旧库**上才有意义地处理，因此随第 2 项一起到 S31。

## 4. 追记：对账作为验收步骤作废，工具保留（2026-09-12）

本节为追加记录，不改写上面已提交的结论。

**触发。** 用户决定不要旧版本的数据、也不要旧代码（计划 §19）。F4 整体作废，S28 的状态由「待验收」改为「已作废」。**本步不因作废标记通过**——作废只改变步骤的适用性，不产生完成度。

**作废的是「步骤」，不是「工具」。** 这个区别要写清楚，因为两者在本步是同一个名字：

| | 处置 |
| --- | --- |
| S28 作为 F4 的一环（对账旧库、为迁移背书） | **已作废**：没有迁移，就没有要对账的迁入材料 |
| `crates/storage/src/reconcile.rs`、`Store::reconcile`、CLI 的 `reconcile` 子命令 | **保留且仍在用**。它是对**本库自身**的诊断——逐输入处理状态、失败原因、无处理状态的输入、字段与证据可追溯性、身份状态与多源实例、两条水位——这些问题的对象是对象模型自己的队列与证据，与迁移来源无关。故本轮只删迁移实现，`reconcile` 一字未动 |

第 2 节各项结论的**证据基础**（5 项测试、内存库）随作废不再有对应的验收流程，但工具本身可复跑，结论若需复核仍可重跑同一命令；**不再据此声称 S28 通过**。

**第 3 节遗留问题的去向**（原文不改）：

1. **「可恢复性」是人的判断**——仍在。这不是迁移问题，是工具与人的分工，保留。
2. **未在一致性副本上跑过完整迁移**——随作废消失。**一致性副本上的完整对账不再有对象。**
3. **抽样清单上限 50 条、截断时不注明「还有更多」**——**已知呈现缺陷，本轮不修**。它原本排在 S31 完善，随 S28/S31 链条变动失去归属；按计划 §19.7 记为随作废不再处理。**缺陷仍在**：清单被截断时输出里看不出来。
4. **S27 留下的两条**（被清理输入的边界记录、事件记录缺世代）——随 S27 作废（见 `S27-migration.md` §6）。两者都与「迁移是否诚实」有关，不再有处置对象。**注意第二项的含义变了**：事件世代曾经是「迁移缺一段信息」，现在只是「旧 `records` 行留在原地、永不投影」的一部分，不再需要补世代。

**旧行留在同一个库里、永不投影**（计划 §19.4）：升级后的 `history.db` 保留约 1.98 GB `records`/`snapshots` 行。`Retention`/`SetRetention` 是活接口，按 `records` 最早时间裁剪；本机当前 `retention_mode = unlimited`，故现在不会被清掉。
