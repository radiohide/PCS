## 已确认的独立问题

### 1. 完整快照和证据持续累积，尚无保留上限

- `target/desktop-preview-data/history.db` 约 8.62 GB；初次页统计为 2,104,747 页，每页 4096 字节，空闲页为 0。该次文件检查的 WAL 为 0，不能归因于单纯 WAL 未回收。
- 库内设置为 `retention_mode=unlimited`、`pruned_units=0`。虽然保存了 `quota_bytes=5000000000`，无限增长模式下不能将它当成已生效的 5 GB 限额。
- 最早保留单位时间为 `2026-10-12T07:41:41.278Z`；检查时约已运行 17.8 小时。只读检查期间，快照约 12.9 万条、证据和投影队列累计约 164.8 万项、历史记录约 17.8 万条。
- 已完成的覆盖索引统计显示，`pcscope.shell.registrations` 有 1,166,814 项证据，约占总证据 71%；它是证据数量的主要来源。这是条数占比，不是磁盘字节占比。
- 最近 3000 份快照覆盖约半小时；外壳登记 5 轮产生 38,351 个条目和约 1467 万字符的完整材料，防火墙规则 3 轮产生约 859 万字符。抽查同一登记的相邻两轮条目完全相同，但仍保存为新快照材料。
- 代码依据：`crates/storage/src/lib.rs` 的 `store_snapshot` 保存整份材料，`evidence::record_snapshot_items` 为每项创建证据和投影任务；即使旧对象数据未变，`ingest` 仍调用 `store_snapshot`。每来源分片还会保留空快照。

结论：已确认有持续的存储与索引放大，需要单独修复。未做全库逐页体积扫描，因此不能把全部 8.62 GB 精确分配给某一张表或某一来源。

### 2. 简单设置读取仍可能被写入和投影阻塞

- `crates/service/src/main.rs` 的 `Request::MonitoringSettings` 通过共享 `state.store` Mutex 读取设置。
- `crates/service/src/projection.rs` 的投影线程持有同一写入锁处理一批最多 64 项。64 是条数上限，不是持锁时间上限；采集入库也使用该锁。
- 同一份监控设置在独立只读 SQLite 连接中可立即读取；检查时队列有约 8980 个待处理项、0 个失败项。随后另一份只读快照显示约 9023 个待处理项，最早待处理编号相同。该现象说明仍有处理积压，但不足以单独证明死锁或确定是哪一次调用占锁。
- 因此，已知的 `monitoring_settings` 10 秒超时与共享锁设计相符，仍需有针对性的持锁耗时或请求诊断，不能仅凭本次读库断言唯一根因。

建议小范围修复：把无需写入的设置读取转到独立只读连接；投影除条数限制外增加时间预算与持锁耗时观测，避免轻量页面依赖长写入批次。

### 3. 仅观察时间变化也被记成模块发生变化

- 抽查最近 3 条 `pcscope.execution.modules / object.changed`：前后 `module_base`、模块路径、大小、进程及启动时间等相同，唯一不同字段为材料内部的 `observed_at`。
- 这会制造没有实际模块变化的历史记录，增加写入，也使用户误以为系统组件不断变化。
- 代码依据：`crates/storage/src/lib.rs` 的快照差异比较将条目的完整 `data` 交给 `sensitive::equivalent`；采集材料中的观察时间因此参与状态比较。

建议小范围修复：区分观察元数据与模块实质状态。新的观察时间和原始证据应保留；仅观察时间刷新时，不应生成“模块变化”动作。回归需要覆盖真正的路径、文件身份、基址、大小等变化，不能简单忽略所有时间或数值字段。
