# 0.2.16 采集写入等待整改

日期：2026-10-20。产品 0.2.16，模型 1.2.7，结构 10。状态：实现、工作区回归、固定目录构建和最终隔离后台验收完成；正式增强后台更新待本次构建授权，当前正式后台仍是已授权的 0.2.15。

## 问题与修改

0.2.15 正式库验收发现，采集已经提交后，还会在公共写入锁内执行 `wal_checkpoint(TRUNCATE)`。历史查询持有读取事务时，该操作等待读者结束，最长受连接的 5 秒忙等待限制；连续多个采集信封可反复等待。期间模型和展示线程也在等待同一把锁。这与已提交材料是否持久化是两件事。

普通采集提交后改为 `wal_checkpoint(PASSIVE)`，只合并当前可以处理的页，不等待历史读者退出。`synchronous=FULL`、事务提交顺序、去重、采集周期、投影队列和容量规则保持原有行为。容量维护仍使用原来的回收及显式检查点路径；该修复不宣称配额不足时能够继续无限接收。SQLite 的行为依据见 [检查点模式](https://www.sqlite.org/pragma.html#pragma_wal_checkpoint)及 [WAL 提交与检查点](https://www.sqlite.org/wal.html#checkpointing)。

隔离计时覆盖当前正式库使用的无限历史模式。滚动配额模式的容量维护仍可能等待读者，既有容量回归通过不等于该模式的并发性能目标已通过，P06 继续开放。

未修改展示内容或其规则指纹，升级应继续使用 0.2.15 已完成的展示工作，不因版本号变化再重建一次。

后台另增加固定大小的内存计数，分别记录模型和展示等待写入锁的耗时、实际处理耗时、批次及最大值。记录随现有状态响应返回，不写入历史、不创建采样任务，便于正式验收继续定位未解决的积压；尚不能据此宣称积压已经消除。

## 隔离测试

新增真实文件数据库回归 `committed_collection_does_not_wait_for_an_active_history_reader`：先打开并实际读取一个历史事务，保持它不结束，再从采集入口提交新快照。修复前单次约 2.16 秒，超过 1 秒断言，测试失败；修复后同场景通过。

扩大到持有同一个历史读事务的 100 次真实提交：p50 8.97、p95 13.12、p99 14.66 毫秒，全部低于 1 秒。每次都重复发送以检查去重；旧读者仍见到原先 1 份快照，新读者见到 101 份，关闭后重开也保留 101 份，同步级别仍为 FULL。这是小型合成材料的存储测试，不是正式大库或完整采集端到端吞吐。

完整工作区回归通过：契约 277、存储 202、后台 28、兼容适配器 1、软件 1、监督器 1、USN 4 项；IPC 5 项在分离的普通用户 Medium 测试副本上通过。增加耗时计数后，后台 28 项再次通过并重新构建；未重新运行没有变更的其余用例来增加计数。查询契约 17 个样本、消费者、产品提示及生命周期登记一致性检查通过，545 个源码及文档文件均有归属。

固定正常／debug 目录核对 11 项运行文件，现有路径配置保留；最终正常目录程序在关闭采集的隔离库中完成启动、真实 IPC、对象／时间线和展示准备、耗时字段检查及正常退出。展示规则指纹与已部署的 0.2.15 相同；正式增强后台原进程保留。构建过程中清理约 481 MB 的已验证旧运行文件，仍在使用的后台副本保留。

## 优化运行构建与性能复测

正式 0.2.15 原包为未优化的 Rust 调试构建。30.76 分钟观察跨度内共取得 26 个成功采样，后台始终为同一增强进程；原始记录增加 4,972 条、快照增加 8,113 份，解析待办曾降至 310，恢复采集后又增长至 76,028。期间一次 IPC 响应中断后恢复。展示仍在推进且无新增展示失败，原有解析失败保持 4 条，但处理能力没有跟上输入，因此仍未通过部署和时效门槛。

0.2.16 最终日常包改用标准 release 优化构建的 Rust 后台及运行依赖；正常目录和桌面 debug 目录保留原入口与配置，11 项运行文件一致。桌面前端仍使用现有开发构建。`scripts/stage-dev.ps1` 新增显式 `-RuntimeProfile release`，默认 debug 行为继续供已有开发测试使用；项目约定明确日常性能包使用 release。没有另建发布目录。
