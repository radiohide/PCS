# 日志分类可见性与关联审查 · 0.2.25

## 已确认的问题

正式库中 206 条 radiohide 登录失败记录已完成解析和展示准备，`target_type=account.user`、`visible_main=1`，但都没有 `instance_id`。旧查询的类别和类型条件只查 `object_instances`，因此选择“用户与账户”或“用户”返回 0 条；未关联记录开关选“也显示”仍无效。

不加类别、仅选登录失败时，旧后台通过全局时间索引查找少量事件，为确认结果结束扫描大量无关记录，实测 6,010 ms 超时。

分类不应以对象关联成功为前提。事件是什么、属于哪个具体对象、对象现在是什么状态，是三个不同判断。

登录成功、计划任务开始/结束、进程启动、注销等已转换动作在这次盘点中均有对象关联。因此不是整个关联框架全部失效，但分类与关联耦合是通用查询缺陷。

## 关联逻辑仍需整改

### 账户：只有 SID 的单一路径偏保守

206 条失败日志的目标字段一致：`DESKTOP-577R9RL\radiohide`，`TargetUserSid=S-1-0-0`。该值不是账户 SID，不能直接建立身份；`SubjectUserSid` 表示发起者，也不能替代目标 SID。

`account_event_target` 当前只检查有效目标 SID，没有继续利用目标域、账户名和历史账户清单。正式库确有 radiohide 对象，其账户清单首次记录于 10 月 15 日；其中 134 条失败日志晚于该时间，值得做历史匹配。134 是候选数，不是已经验证、关联的数量。

下一步：限定同一计算机和安装环境，根据事件时点的域/计算机名、账户名历史及唯一账户身份建立匹配。保留匹配来源和原日志；重名、重建账户、改名和清单覆盖以前的事件不能用当前名字直接归并。关联历史不改变账户启用状态。

### 会话：启动信息没有接入解析上下文

`projection::project_pending` 构造 `AdapterContext` 时将 `boot_id` 固定为 `None`。而正式库已经有启动时间 `2026-10-14T09:44:32.2057530Z`。这不是单纯的系统不提供信息，而是采集信息尚未用于关联。

后一次只读检查中，8,687 条原始特殊权限日志有 5,382 条发生在该启动时间之后，可以优先核对相应启动区间。不能把当前启动信息套到更早的导入日志或历史启动周期。

下一步：建立有证据边界的启动区间，把事件时间映射到对应区间；登录、特殊权限、注销和终端会话使用统一的启动周期身份规则。回归跨重启复用编号、晚到日志、导入日志、时钟变化和旧关联修复，避免新旧规则产生重复会话。

### 更新：事件归属和当前安装状态混在一起

`source_gaps::update_history` 无条件输出未关联，理由是历史操作不证明更新当前安装。这个理由可以约束当前状态，却不足以排除事件归属。

现有 `software.system_update` 清单仅来自 QFE，身份为热修复编号；更新历史还包含更新 GUID、修订号和其他范围。下一步应建立准确的更新身份映射，能匹配的关联，超出 QFE 的更新保留独立历史身份。不能仅提取标题中的 KB 编号就强行合并，也不能把“发生过安装”写成“当前已安装”。

### 原始日志解析覆盖是另一层问题

原始日志中还有 Security 4799、WMI 5857、组策略系列及其他任务计划程序等事件。部分尚无对象动作映射；同一任务执行的不同原始事件也可能归并成一条动作。原始计数不能直接减去动作计数当作丢失数。

本次修复覆盖已转换、有目标类型的动作，不宣称所有原始事件都已经能在时间线找到。后续需按“通道＋提供程序＋事件编号＋版本”核对每种规则、动作引用和跳过原因，明确诊断日志入口及未支持清单。

## 本版实现与边界

- 类型/类别筛选同时接受已关联对象的类型，以及未关联动作的已知 `target_type`。
- “暂时隐藏未关联日志”继续生效；具体对象历史不会因同名而扩大关联范围。
- 稀疏动作类型先获取最多 10,001 个候选，数量不超过 10,000 时直接读取候选并排序；密集动作沿用时间索引。
- 类别/类型候选包含已知类型的未关联动作，不再在性能优化阶段丢掉这些记录。
- 新增动作类型索引和未关联目标类型的部分索引。读程序不要求这些索引预先存在；正式库只读验证未创建索引。
- 未改变采集、对象关联结果、原始记录、展示规则版本或历史回填进度。上述关联整改项尚未实现，不能因本版能显示记录就标为已解决。
