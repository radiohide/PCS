## 1. 收口的判据是「谁在读字段」，不是「谁在用查询」

「无自定 DTO」不是不让页面显示东西，而是：**从响应里读一个字段，这个读取必须落在某个检查得着的地方**。渲染模块声明它读取的 90 条契约路径并逐条受检；页面模块只允许读两样：

- `status`——控制流（空、不受支持、部分成功），不是展示；
- `page`——游标与是否还有下一页，是调用方走完结果集的方式。

**其余字段一律经渲染模块。** 一个自己格式化响应字段的页面，等于悄悄建了第二套契约视图：字段被改名时它照样编译、照样渲染，只是从错误的字段渲染出大致正确的样子。

## 2. 收口过程中检查抓到了我自己

我上一步给系统配置页加的迁移状态面板，**自己读取了 `response.data`、`response.catalog_version` 并拼了视图**——新写的代码第一次跑这条检查就失败了。修法是把那段渲染移进渲染模块（`migrationStatus`），页面只做路由。

这条值得记下来：规则不是我事后回顾出来的，是**先立起来、然后立刻拦住了我的下一处改动**。

## 3. 边界：旧的对象读取已停用，配置类操作仍在

| 类别 | 状态 |
| --- | --- |
| 对象读取（timeline、timeline_search、objects、object_search、snapshots、compare、task_evidence、event_related） | **前端调用为 0**，由检查钉住 |
| 配置与控制（status、plugins、item_controls、retention、privacy、file watch 及其 setter，共 13 个） | **仍在使用**，属系统配置与采集控制 |

第二类**不是查询契约的覆盖范围**——R05 的七类查询全部关于对象、覆盖与投影，不含设置读写。它们的收口属 S33 的兼容路径清理，不在本步。

因此本步的结论是**分层的**，不是笼统的「已收口」：**对象展示已完全经契约并受检；设置与控制的旧通路仍在，且已在检查里显式登记其存在**（`CONFIGURATION` 列表），不会随旧对象通路一起被误删。

## 4. 遗留问题

1. **界面未在真实 WebView 中打开过**（同 S23–S25）：本步验证的是「谁读字段」与「路径是否存在」，不是像素与交互。
2. **服务端的旧对象操作仍在**（`Request::Timeline` 等）：前端不再调用，但它们仍编译、仍可被调用。按计划属 S33 的清理范围；`check-query-consumers.cjs` 保证前端不会回退到它们。
3. **动作查询的游标未实现**（S22 遗留）：状态对比页仍只对比最近 200 条动作，无「还有更多」提示。
4. **13 个配置类操作的响应形状仍由各页面自行解释**，没有像查询契约那样的固定响应集与路径检查。若日后要为配置响应建立同类契约，那是新一轮工作，不在本步范围内。
