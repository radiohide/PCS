## 1. 预检：正本是什么，以及 `--preflight` 会写库

真实库的形状（以 `mode=ro` 打开，未写入）：

| 项 | 值 |
| --- | --- |
| schema | `user_version = 4`——模型表一张都没有 |
| 文件大小 | 1,982,914,560 字节 |
| `records` | 178,130 |
| `snapshots` | 79,370 |
| `objects` / `object_times` | 34,401 / 34,401 |
| 采集范围 | 502 个 `source/scope` |
| `checkpoints` | 117 |

**`migrate --preflight` 不是只读的。** CLI 在分派子命令之前先调 `Store::open`，而 `Store::open` 在打开时按 `user_version` 迁移 schema。实测：对一个 schema 4 的副本执行 `--preflight`，退出码 0，`user_version` 由 4 变为 8，并建出 `evidence`、`object_instances`、`projection_queue`、`projection_state` 四张模型表。

也就是说，名为「预检」的这一步在执行任何检查之前，就已经完成了切换的 schema 部分。**预检只能对副本跑**；对正本跑 `--preflight` 等于已经切了一半，且此时旧二进制再也打不开它（见第 5 节）。

## 2. 一致性备份

用 SQLite 在线备份 API，源库以 `mode=ro` 打开。不用复制文件：该库带 WAL 与共享内存文件，只复制主文件可能得到撕裂的副本。

产物：`%LOCALAPPDATA%\local.pcscope.desktop\backups\history-20260912-115032.db`（**在数据目录下，不在仓库里**），1,982,914,560 字节。校验三项——`user_version` 一致、逐表行数一致、`PRAGMA integrity_check` 为 `ok`。

**正本至今未被改动**，本步结束时复核：`user_version` 仍为 4，5 个设置项、四张旧表计数、117 个检查点与备份逐项相同，无 `migration_state`。

另用 `target/s32-shape.py` 把正本与备份的设置、检查点与旧表计数导出为 JSON 后对比：**完全相同**。备份是切换前的忠实快照，第 5 节的回退演练就建立在这一点上。

## 4. 真实副本上的迁移演练：两处缺陷

演练在备份的副本上进行，两轮。第一轮暴露一处缺陷，修复后第二轮暴露第二处。

### 4.1 旧库的载荷不带信封，回放全部被拒

旧库写在 `snapshots` 里的是快照自身的字段——**一条记录，不是一条消息**，因此没有 `protocol_version` 也没有 `request_id`。而回放走的 `pcscope_contracts::parse` 要求这两个字段。

实测（修复前）：演练每走一条，`problems` 就加一——进度里两个计数逐行相等（`snapshots 74200/79872 · problems 74200`），也就是说**走过的每一条保留快照都被拒**，没有一条例外。演练在走到 74,200 条时被停止，没有走到结尾；剩下 5,170 条保留快照未再单独观察，但被拒的原因是**载荷形状**而不是某几条数据的问题，对这一批同样成立。

第二阶段的 `replayed` 因此在整个演练过程中保持 0：它一条都没有接受。旧库的历史以这种方式被静默地留在原地——退出码干净，产出为零，而这正是迁移存在的意义所要防止的那件事。

S27 的两项回放测试之所以通过，是因为夹具写入的载荷带着信封，而真实旧库从不写信封。已在 `S27-migration.md` 第 5 节追记，不改写其原有结论。

修复：新增 `stored_snapshot`，**只在**信封字段缺失时补上 `protocol_version` 与 `request_id`，补完仍走正常契约校验。真正不是快照的材料照旧被拒；已声明的版本号不会被覆盖。

### 4.2 回放按 OFFSET 分页，且每条证据各自提交

修复 4.1 后迁移能正确恢复历史，但慢到不可用。慢速一轮的实测（`migrate-fixed.log`，11:58:44–12:04:09）：**325 秒内第一阶段走完 502 个范围，第二阶段只走出 2,000 条**保留快照。按这个速度走完 79,872 条要数小时。

（4.1 那一轮的日志看着快得多——114 秒走了 74,200 条——但那是**因为它什么都没写**：条条被拒，代价只有解析。拿它当速度基准会把两件事搞反。）

两处成因，都在 `replay_history`：

- `LIMIT ? OFFSET ?` 每批都要把 offset 之前的行重新扫一遍。`EXPLAIN QUERY PLAN` 直接给出 `SCAN snapshots`——每批全表扫一遍 1.98 GB，而这样的批有约 400 个。代价是历史长度的平方。
- 整批没有事务，每条证据各自提交。库是 `synchronous=FULL`，于是**每条证据一次 fsync**。

修复：改为按 `rowid` 的游标（`WHERE rowid > ?`），并把整批放进一个事务、水位在同一事务内推进。后者本来就是这个模块开头写明的承诺（「Every step is written and the watermark advanced in the same transaction」），OFFSET 版本把它只留给了第一阶段。

观察时间顺带改从已解析的信封里取，不再让 SQLite 用 `json_extract` 把每行的载荷再解一遍。

修复后整轮跑完：退出码 0，**13 分 48 秒**，`finished: true`，`problems: 0`，`replayed: 79872`。两轮演练的结果对照：

| | 第一轮（修复前） | 第二轮（修复后） |
| --- | --- | --- |
| 走过的保留快照 | 74,200（演练在此停止，未走到结尾） | 全部 79,872 条 |
| `problems` | 与走过的条数**逐行相等**，即条条被拒 | 0 |
| `replayed` | 0——第二阶段一条都没接受 | 79,872，即 `snapshots` 表内全部行（含第一阶段写下的 502 条） |
| 速率 | 325 秒走完第一阶段 502 个范围，第二阶段只走出 2,000 条 | 全程 **13 分 48 秒**（含第一阶段），约 96 条/秒 |

### 4.3 迁移只增不改

第二轮的副本与备份对比：

| 项 | 备份（schema 4） | 迁移后（schema 8） |
| --- | --- | --- |
| `checkpoints` | 117 | **117（未变）** |
| `records` / `objects` / `object_times` | 178,130 / 34,401 / 34,401 | **逐项未变** |
| `snapshots` | 79,370 | 79,872（+502，即第一阶段为每个范围物化的那一份） |
| `settings` 既有键 | 5 个 | 5 个，**无一被改写** |
| `settings` 新增键 | — | `model_catalog_v1`、`search_catalog_v1`、`max_pending_projections` |

采集断点连续、用户配置一致、旧表不被清空——三项都成立，且都是**只增不改**。

### 4.4 旧水位不再被信任

`snapshots_done` 在 OFFSET 版本里是「走过了多少行」，而那些行里包含被**拒绝**的行。若把这样一个计数当成游标，回放会从它命名的行继续，从而永久跳过那些被拒的历史——静默地，且以干净的退出码。

因此当水位里没有游标时，回放**从头再走一遍**。重放本身是幂等的（每条证据都以来源声明的地址为键、冲突忽略），所以重复走过的行自然成为空操作，而被跳过的历史得到恢复。新增测试 `a_watermark_from_the_counting_version_replays_the_history_it_had_skipped` 覆盖这一条。

## 6. 阻断项：产品运行时从不执行投影

演练发现：**没有任何运行时路径消费 `projection_queue`。**

证据一，代码里没有调用方。`Store::project_pending` 的调用者只有测试与示例（`crates/storage/src/{flow,faults,migrate,query,reconcile,lib}.rs` 的测试模块、`examples/model-capacity.rs`）。服务端 `crates/service/src/main.rs` 会调 `store.query(`——新模型的读路径——但从不调 `store.project_pending(`；`crates/ipc`、`apps/desktop/src-tauri` 同样没有。IPC 的 `Request` 里也没有触发投影的操作。

证据二，真实运行留下的是空的模型。`data/daemon-s31/history.db`（S31 那次真实采集的库，schema 8，**未经迁移**，因此这批证据全部来自正常采集）：

| 项 | 值 |
| --- | --- |
| `evidence` | 137,257 |
| `projection_queue` | 137,257，**全部 `pending`**，`done` 与 `failed` 均为 0 |
| `object_instances` | **0** |
| `evidence_refs` | **0** |
| `projection_state` | 4 行（objects / facts / actions / coverage），`cursor` 与 `watermark` 均为 `NULL` |

`projection_state` 的游标从未推进过——投影在这个库里一次都没跑过。所以新模型的读路径读的是一张永远为空的表。

证据三，后果是采集会停。S08 按设计加了上限守卫：积压超过 `max_pending_projections`（默认 200000）时 `ingest` 直接拒绝整批（`crates/storage/src/lib.rs:261`）。

把真实历史迁过来会写多少条？**不必外推——演练库本身就是答案。**迁完之后实测（`mode=ro`）：

| 项 | 值 |
| --- | --- |
| `evidence` | 2,687,280 |
| `projection_queue` | 2,687,280，**全部 `pending`**（`done` 与 `failed` 均为 0） |
| `object_instances` | **0** |
| `evidence_refs` | **0** |

2,687,280 条待投影项是上限 200,000 的 **13.4 倍**。真实库的保留快照数与演练库同量级（79,370 对 79,872），所以这个量级直接适用。于是切换后的第一次入库就会被守卫拒绝——按 `lib.rs:261` 的消息形状，实际会读到的是：

```
projection backlog is 2687280 items, above the limit of 200000; run the projection or raise max_pending_projections
```

采集会当场停止。（顺带印证：`object_instances` 与 `evidence_refs` 为零，说明迁移本身也不投影——它只写证据与工作项，把投影留给运行时，而运行时没有这一环。）

这也解释了 `daemon-s31` 那 137,257 条积压：它已经走到上限的 69%，再采一轮就会撞上。

**责任归属：** S07 交付了投影引擎，并如实记下「本机未做真实采集实测」；S08 交付了拒绝入库的上限守卫；此后没有任何一步的记录声称把投影接进了运行时。每一步的记录都诚实，**合起来的产品不投影**。这是 S31 的闭环回归没能发现它的原因——那项测试自己显式调用了 `project_pending`，于是它验的是引擎，不是接线。

**因此本步不执行切换。** 切换到一个永远为空的模型，比不切换更糟：用户会同时失去旧视图和新视图，并且采集会在第一次入库时停住。

## 8. 顺带发现：生成文档与已提交源码不一致（非本步引入）

跑生成器比对时发现一处**先前就存在**的缺陷。它与 S32 的改动无关（本步只动 `migrate.rs` 与文档），但既然撞见了就记下来，交给 S33 的文档交付处理。

**事实。** `scripts/build-*.cjs` 共 5 个。其中 4 个重生成后**零差异**。第 5 个 `build-data-display-reference.cjs` 不是独立的：它以 `target/collector-schema.json` 为输入，该文件由 `scripts/export-collector-schema.ps1` 生成，仓库里没有。直接跑它以 `ENOENT` 失败。

**先跑导出再跑它，产出的文件与已提交的 `docs/collection-to-ui-reference.md` 不一致**（308 增 / 904 删）：

- **行号整体偏移。** 已提交文档指向 `collect-system.ps1:23`，而该文件第 26 行才是 `Emit-Collection 'pcscope.system.version'`；`domains/scoped.ps1` 亦整体偏 2（49↔51、50↔52、58↔60、73↔75）。即**已提交文档的行号引用对不上已提交的源码**。
- **字段表示例与字段表变空。** 已提交文档里有 `"path": "C:\\Example\\item"` 这类示例值与字段表，重生成后是 `"data": {}`、`"fields": {}`。原因是采集侧现在把字段直接写在 `Item` 的哈希表字面量里（如 `collect-system.ps1:28`），而导出脚本仍只从 `Fields`/`Cim-Items` 助手调用里取字段。

**成因。** 文档与两个采集脚本最后一次都由同一个提交 `c124c87` 改动，而文档头部记的实现指纹（`3a72a6d…`）与现在重算出来的（`9465f70…`）不同——**该提交先生成文档、随后又改了采集脚本，两者一起提交**，文档就此停在旧源码上。所以这是 `c124c87` 留下的陈旧产物，不是 S32 造成的。

**为何不在本步修。** 直接提交重生成的结果会让字段表示例**变少**（上面第二点），那是把一处缺陷换成另一处；真正的修法是让导出脚本认得当前的字段声明方式。这属于文档工具链，且计划的 S33 验收里正有「文档示例能对应当前界面」一条。**已把重生成结果还原，未纳入本步提交。**

### 实现

- `crates/service/src/projection.rs`：正式服务启动独立工作线程，使用与采集共享的写连接，每次最多提交 64 条队列项，批间释放锁。启动积压清空前暂缓自动采集，手动采集返回明确提示；此后持续处理新增材料。
- 数据库事务失败保留待处理项，间隔 1 秒重试；无适配器或契约拒绝的条目保留 `failed` 和错误原因，不删除原始证据，也不无限重试确定性解析错误。后续规则修复后的失败项重放不属于本次自动重试范围。
- 退出时等待当前投影事务结束，未处理项下次启动继续。`end_session` 在工作线程停止后写入的会话结束证据同样留待下一次启动，不能要求关机后的队列必为零。
- 机器标识沿用采集器读取的 64 位注册表 `MachineGuid`；采集安装标识保存在数据库设置中，是数据库所属的采集安装标识，不是每次启动重新生成，也不声称是物理硬件身份。不同机器的绑定冲突、已有对象但缺少运行时身份绑定时明确拒绝，避免悄悄生成第二套对象。
- `Status.projection_worker` 提供工作线程状态。`ProjectionStatus` 的对象/事实/动作共享同一实际队列计数，不再把 schema 初始化的零值当作积压与失败状态；原 cursor/watermark 未伪造为完成水位。

### 10.2 全量材料暴露并修复的三处问题

1. **启动记录也被积压护栏拦截。** 初次启动在 `begin_session` 处报 2,687,280 条积压并退出。第 9 节的小规模验证没有覆盖这个条件。现在只有 `internal_event` 的进程内构造路径可越过投影积压门，仍受存储容量约束；外部 `ingest` 即使声明 `pcscope.core` 也不能绕过，已有回归断言。没有提高 200,000 上限，没有清空队列。
2. **逐项重复解析完整快照。** 单项读取接口每次创建新缓存，使连续条目反复解析同一大快照。现在单个事务共享一个快照缓存，并按 item id 索引；缓存不跨事务，切换 run 必须重载，回归验证与原单项读取结果一致。规则指纹改为每批计算一次。
3. **采集健康查询大库超时。** 原联结逐行回表读取证据地址及队列状态，真实 IPC 超过 6 秒被中断。新增 `evidence_source_address` 与 `projection_queue_address_state` 两侧覆盖索引；新库和已有 schema 8 库都会安装，不改数据列或 schema 版本。只加第一条索引仍超时，两条齐全后真实接口约 **4,892 ms** 返回 loaded。对象列表曾测得约 429–624 ms；投影状态稳定区间约 0.32–0.48 秒。首次安装索引会增加启动耗时，不计作稳态查询延迟。

速度记录不是同一材料切片的严格 A/B 基准：修复启动后的原 Debug 约每秒 110 条；快照缓存后的 Debug 约每秒 730 条；Release 稳态曾达到每秒约 1,800 条。并行测试与不同来源使后段速度波动，因此不据此承诺全库完成时间。

按「验收记录不改写已提交的历史结论，需要更正时追加新的记录」，在此追加更正，第 10.3 节原文不改。触发原因：迁移作废后复核这段材料，逐条核对它引用的工具，发现其中一条比对没有实现。

### 11.1 顺带记下的工具缺陷

`audit` 模式**没有失败路径**：它不比较任何东西，也不对打印出来的数字做断言，所以退出码永远是 0。这意味着两件事：

1. **退出码不能当审计结论用。** 谁按退出码判断「审计通过」，得到的都是「文件打得开」。10.3 的「缺失或改写均为 0」不可能出自这个退出码——它只能出自读 JSON 的人。
2. **它在 10.4 里的用途是对的，但那是因为读的人对。** 该模式的实际价值是**如实打印阻断项的计数**，而 10.4 恰恰是从这两个 JSON 里读出来的。这一点无需修改工具即可成立。

本轮的处置只是**更正记录**，不改工具：迁移已作废（见 `docs/full-object-refactor-plan.md` §19），这个 example 连同它服务的 `s32-scale-*` 副本只服务于迁移演练。是否回收、是否给 `audit` 补断言，随演练材料的去留一并决定。
