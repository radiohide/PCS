# 系统对象列表响应修复验收

日期：2026-10-13。针对默认“系统对象”列表超时、监控信息读取长时间等待，以及筛选类别仍有英文的问题。实现说明见 [共享变更](../shared-changes/0012-object-query-responsiveness.md)。

## 根因与修复范围

对象列表本身取 50 行不是主要瓶颈。列表摘要需要对观察引用的证据地址精确去重；当前数据中约 158 万条引用只有约 6.2 万个不同地址，原查询反复处理同一地址并建立临时去重树。新的覆盖索引允许逐个跳到下一个不同地址，再核实是否有满足当前筛选条件的对象引用它。保留精确计数、小范围按对象统计、分页窗口和旧只读库无新索引时的兼容路径。

首次运行验证暴露了分类查询路线不适合稀疏引用的问题，随后补测全部 12 类并修复：四项统计共用一次筛选结果；接近全量对象直接逐地址统计，其余按总引用规模进行最多 25 万条的有界探测，选择合适的统计路线。空选择短路；没有新索引的旧库不做探测。选择过程是性能估计，返回值仍为精确计数。

轻量设置和状态读取改用独立只读连接，避免等待采集与投影的共享写锁；内存状态锁不包围数据库写入。后台替换直接请求指定实例平稳退出，并在取得独占管道后才打开数据库。桌面仅在管道确实不存在时启动后台，已有后台超时不会再触发重复启动。

类别补齐“用户与账户”“文件与文件夹”“运行程序与会话”。对象列表超时提示提供本页实际存在的类别、类型和名称筛选；内部错误保留在折叠详情中。

追加修复同页“最近变化优先”引用不存在排序字段的问题。列表、详情、排序及分页边界统一使用同一变化时间表达式；无变化历史按空值处理，同时间对象按内部身份稳定排序。

## 隔离数据测量

从当前开发预览库只读分批复制查询所需表到隔离库；没有复制全部原始材料，也没有向原库手工创建索引。观察引用共 1,581,291 条；复制读取单批最长约 167 ms。

| 项目 | 测量结果 |
| --- | --- |
| 原证据地址精确统计 | 4003 ms，62,356 个地址 |
| 逐地址跳跃统计 | 624 ms，相同 62,356 个地址 |
| 首次索引建立 | 9.21 秒 |
| 索引增加空间 | 355,299,328 字节，约 339 MiB |

以上是隔离副本中的 SQLite 候选查询测量，不等同完整原生请求或任意规模保证。最终完整原生开发构建默认 50 行首两页为 1860 / 2162 ms，首次计数仍为 62,356；五种排序各两页范围为 1735–2397 ms。12 类全部通过，其中运行程序 927 ms、网络 1060 ms、资源管理器扩展 3612 ms。连续两页的进程峰值工作集约 23.7 MiB。查询预算仍为 6 秒，没有以放宽超时或删除历史取得结果。
