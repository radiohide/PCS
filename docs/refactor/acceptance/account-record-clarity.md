# 账户记录归类与显示修复

日期：2026-10-13。针对“用户（名称尚未确认）”“账户权限（名称尚未确认）”及无法解释的“对象尚未确认”。

## 实际原因

只读查询当前开发后台，用户所报 2026-10-12 15:54:00 对应实例 43。它只有 Application 日志关联，没有账户观察或名称事实。已有事件证据核验明确判定来源与原分类不符，按普通系统事件返回；旧占位对象仍保留在对象列表，通用文案却暗示是一个“最近仍在”的用户。

实例 973 是旧 `identity.special_privileges` 事件汇总占位，缺少账户与权限身份。Windows 4672 表示某次新登录获得特殊权限，不是持久账户权限配置。适配器原来把它映射到 `account.right_assignment`，而该类型需要“账户＋单项权限”，因此不断刷新无法确认的占位。来源目前能正常读取，不是未获得管理员授权。

实例 147 是已确认的实际权限配置，详情已含 `SeRemoteInteractiveLogonRight`，但列表摘要未选择 `privilege`，界面也没有中文权限名。另发现实例 1076 将空账户 SID `S-1-0-0` 当成已确认账户；该值不代表一个可识别用户。

此次检查还复现同一来源项展开多项权限/组成员时，共用父记录绑定导致后续子项误合并的问题。必须修正投影，不能只给错误记录添加名称。

## 修复边界

- 账户事件只使用目标账户的有效 SID；不借报告事件的主体账户填补目标账户，不将受保护字段或空 SID 变成身份。
- 4672 保留为“登录获得特殊权限”事件。只有明确的事件启动周期和有效登录标识才可关联会话；缺少时保持未关联。当前启动周期不能用于猜测旧事件所属周期。
- 多项权限和组成员分别按子项身份解析，普通单对象来源原有重命名和身份补全规则保持。下一次有效完整采集可补足当前子项；不手工重写实际历史。
- 账户摘要包含权限内容、账户启用状态与最近登录资料。`record_basis` 是兼容旧后台的可选展示字段，区分实际观察、仅日志提及及未知依据，不改变存储身份或生命周期。
- 无名日志记录显示“日志中的账户记录”“日志中的权限记录”；资料不足显示“信息待补全”。活动状态显示“最近有记录”，不表示正常运行或账户仍在使用。
- 已知权限显示中文含义，未知权限保留中性名称，原值置于详情。普通来源名称优先，受保护资料不从其他路径恢复。
- 历史错误归属由读取时重新核验，不能继续作为对象已确认的活动。原始证据和旧关联保留以便追溯。
