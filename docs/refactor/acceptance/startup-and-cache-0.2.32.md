# 启动诊断与展示缓存版本校验：0.2.32

2026-10-22。接续 0.2.31，优先处理正式后台启动和性能验收的阻塞。

## 本次现场事实

- 同账户 UAC 启动的冻结 0.2.29 随后退出。只读检查发现结构初始化和一条异常退出恢复记录已写入，但本次 `collector.started` 与心跳未写完。原启动方式未保留 stderr 和退出码，具体退出原因尚未确定。
- “早期客户端断开使首次管道连接失败”的隔离实验没有复现该猜测，因此没有据此修改管道接受逻辑，临时诊断测试已移除。
- 用户授权后请求再次用同一份 0.2.29 保存错误日志；Windows 返回“操作已被用户取消”，诊断启动程序未运行。没有新的退出日志，也没有把普通权限启动当作增强采集验收。
- 正式后台仍关闭，正式负载性能及正式 UI 验收未通过。正式历史和配置没有被清理；0.2.30/31 的历史修复还未在正式后台执行。

## 已修复与新增能力

1. 只读查询发现：新版读取程序面对旧版已发布的展示缓存时，只检查 `published`，随后却以新版 revision 筛选缓存，可能将已有历史返回为空。现在同时核对版本，不匹配时走既有原始模型查询路径；读取不触发迁移或重建。
2. 性能工具在计时前核对读取程序与已发布展示缓存的版本，未准备完或不匹配则明确拒绝测试。结果附应用版本和展示规则版本，避免把空列表的快速响应当作优化成绩。
3. 后台在所选数据目录保存 `service-startup.json`：版本、PID、启动阶段、耗时，以及返回错误的完整因果链（最多 4096 字符）。原子替换一个固定文件，不周期采样、不追加无限日志；保存失败仅写 stderr，不覆盖实际启动结果。数据目录解析之前的错误、原生崩溃和外部结束进程仍不能保证有完整退出错误，最后阶段可供排查。

这不是对 0.2.29 退出原因的修复结论。下一次正式启动需要结合保存的错误和退出码判断。
