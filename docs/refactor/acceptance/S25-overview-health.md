## 1. 总览：计数分开，以及「有多少还没接来源」

计划要求「对象类别/类型数量、近期动作、来源覆盖摘要；**对象数与证据数分开**」。页面因此给出六个互不相加的计数：对象类别、对象类型、当前对象、来源记录、动作、证据，外加来源状态摘要。

**类型计数里写明其中多少个有来源、多少个尚未接入**：一个没有来源的类型不是「空集合」，而是「没有任何东西喂给它」。把两者显示成同一个 0 会让人以为采集失败了。

## 2. 采集健康：两种失败分开

页面把「来源读不到」与「材料到手但没能变成对象」分列：

- 前者是覆盖行的 `last_result`（采集失败）与开关状态；
- 后者是该来源在投影队列里的 `failed` 计数（解析失败）。

计划第 8 节要求这个区分，而**这两个数必须并排才有意义**——这正是共享改动 0007 把投影计数放进覆盖视图而不是另开一条查询的理由。已停用的来源单独标出：**停用不是失败**，把它算进失败数会让人去找一个不存在的问题。

## 3. 清掉的死代码

旧时间线的机械（`pretty`、`eventRows`、`detail`、`showEventDetail`、`bindEvents`、`loadTimeline`、`displayName`）在页面改读模型之后**只剩定义、没有任何引用**。已全部删除。

留着它们的代价不是几行代码：它们看起来仍属于页面，而读代码的人会以为某条路径还在用。这与 R09 那次删掉的不可达分支是同一类问题。

`state.events` / `state.selected` 保留——系统配置页的隐私开关回调仍在清空它们。

## 4. 遗留问题

1. **插件页的映射是生成物，不是手写的。** 它是仓库里三样东西的连接（来源映射、目录、适配器覆盖），由 `build-source-type-map.cjs` 生成、`check-source-type-map.cjs` 保证不过期。**过期的生成物比手写的更糟，因为它会被信任。** 其中「尚未接入」的 7 个来源与 S21 对账点名的完全一致——两处独立得出同一结论。
2. **系统配置页保留四页签，只新增一处按需展开的迁移状态**（在「历史存储」页签内折叠）：展开时才读取，页面不被内部参数铺满。它把**前端构建时的目录版本**与**后台处理素材时的规则版本**并排显示——两者不一致说明前端需要重新构建。
3. **`stats()` 仍读旧的状态查询**，用于页头「载入最新」的计数刷新。总览页已不依赖它，但它在总览页上会把新的计数块短暂替换成旧口径的计数——因为紧接着会整页重渲染，用户看不到，但这个重叠应当随旧状态的退场一并清掉。
4. **界面未在真实 WebView 中打开过**（同 S23/S24 记录）。
5. **动作查询的游标仍未实现**（S22 遗留）：总览的「最近发生」只取 8 条，不受影响；状态对比页受影响。
