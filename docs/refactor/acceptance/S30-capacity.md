## 1. S02 基线重跑

原有基线工具在 S05–S08 之后**原样可跑、未做修改**：夹具加载、查询矩阵、并发补采与库文件测量全部通过。实测查询延迟：**冷 p95 7.17 ms、热 p95 6.8 ms**（100 次重复，本机、release、示例夹具规模）。

**这是「原样可跑」而非「与 S02 环比」**：S02 用的是改动前的二进制，两次运行的夹具与规模相同但代码不同，逐项环比需要同一台机器上保留两份产物。本步记录的是**当前值**，不宣称与 S02 的差额。

## 2. 容量行为实测（100 轮，每轮 200 项）

| 场景 | 结果 | 结论 |
| --- | --- | --- |
| 稳态（同一份材料重复采集 100 轮） | 事实与动作**逐项不变**；库从 1.47 MB 增至 30.1 MB | 模型的**结论**不随重复采集增长——这是「无垃圾数据」的实质。增长来自每轮留存的证据与索引，属按设计保留的历史 |
| 滚动清理（64 MB 配额） | 100 轮中 52 轮入库、48 轮被拒；库稳定在 22.0 MB，**在配额内**；600 条引用标明已清理；**悬空引用 0**；无原因引用 0 | 配额被遵守，剩余历史可解释 |
| 无限模式（50 轮） | 50 份快照**全部保留**，`pruned_units` 为 0 | 没有任何调度、年龄或容量删除历史 |
| 空间不足（40 MB 配额 + 每轮 4000 项） | 入库**被拒**（未假报成功） | 见第 3 节第 1 项——**本步修掉了一处真缺陷** |

组件占用：SQLite 的索引与数据同在一个文件内，因此 `database` 包含索引；`wal` 与 `shm` 单独计量。

**每轮增长 286,638 字节**（200 项不变材料）是一个**需要留意但没有结论的观测**：真实规模的软件清单或 USN 批次远大于 200 项，按此线性外推，5 GB 默认配额下的可保留轮数需要真实负载实测。列入第 3 节第 2 项。

## 3. 本步修掉的缺陷

**空间不足时报的是存储引擎自己的错，用户读不懂。** 配额用页数上限强制，超限时从某次 INSERT 深处冒出的是 SQLite 的 **`database or disk is full`**——既没说撞到的是哪个限制，也没说能做什么，读起来像磁盘坏了而不是一个设置。

已修：`Store::ingest` 现在把该错误翻译为库自己的说明——**「已达到配置的容量上限，本批材料未能保存；采集端可以重发。请在设置页『历史存储』提高配额，或改用无限增长模式。」** 检查同时断言三件事：不是引擎原文、点名限制、给出出路。

这是 S30 要求交付的「优化结果」的第一条，也是**只有跑真实容量场景才会暴露**的一类问题：单元测试里配额从不被撞到。

## 4. 遗留问题

1. **5 GB 实测未做。** 本步用的是 40–64 MB 的配额与示例规模，用于验证**行为**而非**容量**。计划第 12.4 节的门槛与 5 GB 的真实回收需在真机、真实盘、真实负载下测——属 S31 与发布前。
2. **长跑下的增长曲线未测。** 稳态 100 轮是几分钟的负载，不构成「持续运行下无增长」的证据；72 小时长跑属 S31（且需真机）。
3. **高事件输入的路径未单独测。** 本步测的是快照来源；事件批（`event_batch`）的入库与投影开销未单独测量。事件与快照的每项开销结构不同（事件还写 `records` 与去重表），需要单独一轮。
4. **未与 S02 做逐项环比**（见第 1 节）。
5. **清理与投影并发的容量行为未测**（S29 记录第 3 节第 3 项顺延）。
