## 1. 时间线：两条不能违反的规则

- **无法归属的动作显示为未归属，并带上原因，不链接任何对象。** 把它归到最近的一个对象名下是时间线唯一不能做的事——那会让它读起来像关于那个对象的事实。查询默认包含这类动作，页面把它明确标出来。
- **推导的时间标明推导。** 区间是变化生效的跨度，上界是**界限**而不是发生的时刻；页面写成「区间 A → B（时间为推导）」，而不是把它摆进「发生时间」的位置。

## 2. 状态对比：从快照载荷改为观察版本

旧页面对比同一来源、同一范围的两个快照载荷；新页面比较**一个对象的观察版本**——字段从什么变成什么，以及这个变化在哪个区间内生效。三条规则都是模型已经定下的，不是排版选择：

| 情形 | 页面怎么写 | 依据 |
| --- | --- | --- |
| 一侧没有值 | 显示「这一侧没有值」，并附一行说明「缺失不是删除，因此这里不写成『已移除』」 | R04：缺失不是值 |
| 区间动作 | 显示区间并标注「时间为推导的区间上界」 | R04 §1：区间用上界，且派生锚点必须可见 |
| 对象已结束或已删除 | 页面顶部给出说明：这个对比的含义与「对象仍存在」时不同 | 计划第 8 节：生命周期不同不默认直接比较 |

## 3. 检查被重新对准，而不是放宽

`check-collection-view.cjs` 从 `const timelineFilters=` 起加载 app.js 并驱动时间线页的筛选处理器。页面改写后它**正确地失败**了。处理方式是**重新对准**：现在断言的是页面**构造的请求**——查询是 `action_timeline`、未归属动作默认包含且只有显式要求才排除、时间范围变成 `since` 下界、清空筛选回到默认。

「筛选悄悄不再发出」正是这里最该防的：页面看起来在收窄结果，实际什么都没筛。

## 4. 遗留问题

1. **界面未在真实 WebView 中打开过**（同 S23 第 3 节第 1 项）：验证的是渲染器与契约的一致性，不是像素与交互。
2. **动作查询的游标未实现**：**状态对比页依赖它**——对比页取该对象的动作时传 `limit:200` 且不使用游标，因此动作超过 200 条的对象只对比到最近 200 条，且页面没有提示还有更多。这是本步最需要补齐的一处，属 S22 遗留的延续。
3. **总览页仍走旧查询**，时间线页的「立即采集」按钮走旧的采集入口，属 S25/S26 范围。
4. **`since` 的时区**：页面用 `new Date(...).toISOString()` 生成 UTC 下界，与存储的规范时间一致；但页面上没有显示这个下界具体是什么时刻，用户只能从选项名判断。
