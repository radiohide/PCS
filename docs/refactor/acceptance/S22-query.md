## 1. 分页为什么是这样写的

**一次遍历有自己的水印。** 水印由两部分组成：**查询指纹**（筛选与排序的摘要）和**起始时的存储状态**（证据序号与实例编号的上界）。

- **指纹决定游标属于哪次查询。** 筛选或排序不同却拿同一个游标回来，是把两段页序列拼在一起——直接拒绝，而不是按新条件重新解释。
- **状态上界决定窗口。** 一行在遍历开始后才到达时，它属于**下一次查询**，不会被塞进调用方已经走过的那一页。新的查询是新的水印，也就能看到新行。

这两条合起来才是「数据到达时分页仍稳定」。写第一版时我把游标位置当成了窗口上界，第二页因此被排空——测试立刻抓到了。

## 2. 一次查询的三种"没有结果"分得开

| 情形 | 状态 | 说明 |
| --- | --- | --- |
| 匹配零行 | `Empty` | 查询成功，只是没有行 |
| 游标来自另一次查询 | `Unsupported` + `stale_cursor` | 不是"没有行"，是"这个游标不是我的" |
| 引用不存在的实例 | `Empty` + `unknown_instance` | 明确告知，而不是返回一个空白对象 |

## 3. 顺带修正的一处显示质量

实例的 `display_name` 原本在分配时取自身份字段，而计划任务的身份只有路径，于是列表里显示的是 `\A\task-00` 这样的**路径**而不是名称。改为**名称字段到达时更新显示名**——身份字段是兜底，不该是首选。排序与搜索因此都按名称工作。

## 4. 遗留问题

1. **动作查询的游标尚未实现。** `InstanceActions` 接受 `cursor` 但当前忽略它，只返回首页；实例动作数通常有限，但契约允许分页，需在 S23–S25 接页面时补齐。
2. **`coverage` 请求不筛选历史状态。** 它返回全部覆盖行，未按 `history_state` 或来源开关筛选——属 S25 的采集健康页范围。
3. **计数口径**：`instances` 是匹配数，`actions`/`source_records`/`evidence` 是**匹配实例的**关联计数（非全库）。三者不相加，与契约「按类计数、不跨类求和」一致，但页面需要知道这个口径。
4. **权限相关状态 (`PermissionDenied`) 未接线**：本机没有多用户权限模型，该状态在契约中定义但当前不会产生。属 S26/S31 范围。
5. **`Unsupported` 目前只用于游标与动作引用**，尚未覆盖"该视图未实现"的语义——七类请求都已有回答，等 S23–S25 出现按页面裁剪的视图时再补。
6. **本机未做真实采集实测**；查询验证在 `:memory:` 上以构造数据完成。
