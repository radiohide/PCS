## 1. 页面读什么，以及为什么这样验

对象页与旧列表的差别是**模型本身有类型、身份状态和逐字段来源**，所以页面显示的是：

- 对象、类型（名称与类别）、身份状态与存在状态（**显示为词，不是代码**）；
- 每个字段的值、来源与状态——「已知 / 来源未提供 / 无法读取 / 冲突 / 已遮罩」是**五种不同的事**，页面不把它们压成空白；
- 动作带上它推导所依据的**区间**，以及「时间为推导」的标记。

**验证方式是契约一致性**：渲染器声明它读取的 85 条契约路径，检查逐条对照 R05 的固定响应集。字段被改名会在这里失败并点名路径，而不是在页面上渲染出一片空白。

## 2. 顺带确立的两件事

- **查询走既有的只读路径**：IPC 的请求类型就是 R05 的 `QueryRequest`（不是副本），服务端用独立 WAL 读连接处理，不抢采集写入锁。
- **显示名不再是路径**：实例的 `display_name` 原本取自身份字段，而计划任务的身份只有路径，列表里显示的是一串路径。改为**名称字段到达时更新显示名**，排序与搜索因此都按名称工作。

## 3. 遗留问题

1. **界面未在真实 WebView 中打开过。** 本步的验证是渲染器与契约的一致性 + 查询层的测试，**没有截图、没有人工走查**。像素级结果与交互属于发布前的人工验收（S31 用户流程回归），本机也未安装 WebView2 运行环境供后台联调。
2. **旧的按采集项分类的列表仍在使用**：总览页、时间线页的「加载更早记录」等路径仍走旧的查询，直到 S25/S32。两套并存是计划内的（S32 统一切换），但页面上同时存在两套概念，需要在该切换时一并处理。
3. **动作查询的游标未实现**（S22 遗留）：对象详情的动作预览取首页，符合当前用途，但长历史的完整分页要等该缺口补上。
