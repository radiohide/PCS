## 1. 两个阶段，以及为什么不是「重新入库一遍」

| 阶段 | 做什么 | 为什么这样做 |
| --- | --- | --- |
| 导入最后状态 | 把旧 `objects` 表按 `source/scope` 分组，**物化为每个范围一份快照**，走正常管线 | 旧库保留的是每个对象最后已知的值与时间；那本就是一次采集的结果，物化成快照让正常管线承载它，而不是为迁移另写一条投影路径 |
| 回放保留历史 | 对旧 `snapshots` 逐条建立**证据地址与投影工作项** | 材料已经在库里；**重新入库不会发生任何事**——回执表会把它当作重放拒绝 |

第二条尤其重要。如果按「把旧快照再喂一遍」实现，迁移会**静默地什么都不做**：完全成功、零错误、零产出。这是本步最容易写错的地方。

## 2. 与入库共用的一个函数

「存下一个完整快照意味着什么」在入库与迁移里必须一致，因此抽成共用的 `store_snapshot`：写入材料一次、为每个 item 建立一条指向它的证据地址、写入让重放成为空操作的回执、记录范围。**两处各写一份，就是日后再分道扬镳的开始。**

## 3. 验收条件对照

| 计划验收 | 结果 |
| --- | --- |
| 任意批次后退出可续跑 | 通过：`a_migration_resumes_after_any_batch`——每批 1 个范围执行到底，与一次性跑完得到完全相同的实例、事实与证据引用计数 |
| 重复启动不重复对象/动作 | 通过：`running_the_migration_again_adds_nothing`——完成后再跑一批，实例、证据、队列三项计数逐项不变 |
| 第一条保留历史不当成真实创建 | 通过：`the_first_retained_observation_is_not_a_creation`——实例的 `first_observed_at` 是旧库的观察时间、`created_at` 为空，且动作数为 0（一次观察是基线，不是变化） |
| 旧材料不覆盖较新状态 | 通过：`old_material_does_not_overwrite_a_newer_observation`——先用较新观察建立当前值，再导入较旧的旧库状态，当前值仍是较新的那个 |
| 被清理的输入有明确处理结果 | 部分通过：无法解析的旧材料计入 `problems` 并记录来源与原因，不中断整批；**已清理的输入**（材料本就不在库中）不会出现在遍历里，其"结果"是**不被处理**——见第 4 节第 1 项 |
| 不自动清空现有库或重置设置 | 通过：`a_migration_neither_clears_the_store_nor_resets_settings`——`records`、旧 `snapshots`、`objects` 均未被删除，`retention_mode` 未被改写 |

## 4. 遗留问题

1. **「被清理的输入」的结论只是隐式成立。** 旧库中被回收的历史不在 `snapshots` 里，因此遍历根本看不到它——**不被处理，但不留下任何记录说明"这里曾有一段被清理的历史"**。计划要求「有明确处理结果」，当前只是"没出现在遍历里"。要真正满足，需要在迁移开始时记录旧库的最早保留边界，并在进度报告里写明"此前的历史已按保留策略清理，本次迁移不包含"。列入 S28 对账时处理。
2. **事件记录（`records` 中的来源事件）没有迁移。** 旧库把事件存在 `records` 里，但**世代（epoch）与断点没有逐条保留**，而事件证据的地址正是「来源 + 世代 + 事件 id」。没有世代就只能编一个，那正是不能做的。快照路径不受影响（材料自带 run_id）。处置方式需在 S28 与 S21 对账时确定：要么承认这部分只能保留原始记录而不进对象模型，要么先补世代信息。
3. **迁移只在内存库上验证过。** 未在真实旧库副本上跑过；真实旧库的规模、异常材料和清理边界都需要实测，属 S28/S31。
4. **未接入来源在迁移中会逐条记为解析失败。** 与 S08 记录第 5 节第 3 项同因：没有适配器的来源，其材料进队列后会被判为失败。迁移大批量导入时这一点会放大，健康页需要能按来源汇总（S25 已做到按来源显示，但未按迁移批次区分）。
5. **暂停与重试是「停止即暂停」的形式。** 迁移没有独立的暂停标志：停掉进程即暂停，再运行即从水位继续。计划要求「提供进度、暂停、重试和错误定位」——进度与错误定位有（`--progress` 与 `problems`），**暂停没有独立开关**，重试即重跑该批。若需要显式暂停/单批重试命令，属后续补充。

## 5. 追记：真实旧库副本上的实测更正（S32）

本节为追加记录，不改写上面已提交的结论。第 4 节第 3 项声明的「迁移只在内存库上验证过……属 S28/S31」在 S32 落地，实测出一条本步未能发现的缺陷。

**缺陷。** 第 3 节里两项回放测试（`the_first_retained_observation_is_not_a_creation`、`old_material_does_not_overwrite_a_newer_observation`）之所以通过，是因为测试夹具写入 `snapshots` 的载荷**带着协议信封**（`protocol_version`、`request_id`）。真实旧库从不写信封：它存的是快照自身的字段，是一条记录，不是一条消息。于是 `replay_history` 走的 `pcscope_contracts::parse` 对真实旧库的保留快照都以 `missing field 'protocol_version'` 拒绝。

实测（真实库副本，修复前）：进度里 `problems` 与 `snapshots` **逐行相等**——走过的每一条保留快照都被拒，没有一条例外。该轮演练在走到 74,200 条时被停止，没有走到结尾，所以「全部 79,370 条都被拒」是**由载荷形状推出**的判断（形状一致，不是某几条数据的问题），而不是观察到的总数；能观察到的是：被走到的那些，条条如此。第二阶段的产出只剩第一阶段刚写下的那 502 条。

**受影响的说法。** 第 1 节表格里「回放保留历史 | 对旧 `snapshots` 逐条建立**证据地址与投影工作项**」这句话，在真实库上从未成立。第 3 节的验收表没有为回放单独列一行，所以**验收结论本身没有被推翻**；被推翻的是夹具形状给测试带来的那份信心——测试通过，而它验的是任何真实库都不会产生的材料。

**修复属 S32**，不在本步改动：`stored_snapshot` 只在信封字段**缺失**时补上 `protocol_version` 与 `request_id`，补完仍走正常契约校验（真正不是快照的材料照旧被拒，已声明的版本号不会被覆盖）；夹具改为真实旧库形状；新增两项测试。修复后的真实库实测结果记在 S32 的验收记录里。

**本记录里随之失效的三处指引**（原文不改，在此指出）：

1. **第 5 节把「信封缺失」的修复指向 S32。** 那次修复的实现是 `migrate.rs` 里的 `stored_snapshot`（`:270-281`，只在信封字段缺失时补 `protocol_version` 与 `request_id`），**已随模块删除**。第 5 节的**结论仍然成立且更有价值**：夹具形状给测试带来的信心可以完全落空，而测试照样全绿——这条判断与迁移无关，适用于任何「测试喂的是真实来源不会产生的形状」的场合。
2. **第 4 节五项遗留问题全部随作废消失**（清理边界记录、事件世代、真实库验证、未接入来源的失败放大、独立暂停开关），**一项都没被解决**。这是作废，不是完成。
3. **「在内存库上验证过」与「真实旧库副本上的实测」这两类证据不再有对应实现**，因此都不可复跑。

**留档先于删代码。** `Store::open` 对旧库原地升级到 v8，跨过之后旧二进制拒绝该库（单向门，实测见 `S32-switch.md:125`）。故本轮**先归档、再动代码**：归档走 SQLite 在线备份 API（不是文件拷贝，`history.db` 带 WAL），落点在数据目录之外 `%LOCALAPPDATA%\local.pcscope.desktop-archive\`，校验 `user_version`、表集合、逐表行数并跑 `integrity_check`，任一项不符即非零退出。理由与规格见计划 §19.4。

**旧行仍在同一个库里、永不投影。** 升级后的 `history.db` 保留约 1.98 GB 的 `records`/`snapshots` 行，不删、不迁、不进新模型。**一个需要知道的交互**：`Retention`/`SetRetention` 是活接口，按 `records` 最早时间裁剪；本机当前 `retention_mode = unlimited`，故现在不会被清掉，但若日后改为滚动模式，这些行会随时间被保留策略删除——参考材料是数据目录之外的归档副本，两者不冲突（计划 §19.4）。
