# 事件适配器：`pcscope.eventlog.*` 的统一入口

日期：2026-09-12。代码：`crates/contracts/src/adapters/event.rs`。归属：S17 的跨类别组成部分。

## 1. 为什么是一个入口

事件素材不是对象素材。一条事件**陈述某件事发生了**、指名它发生在谁身上，对其余属性一无所知——所以它产出的是**动作**，而目标类型来自目录中该动作的 `target_type`，不来自来源。

这也是它不能按来源逐个适配的原因：仅 `pcscope.eventlog.security` 一个来源就到达十几个类型（见 `source-map.cjs` 那一行），而**采集端已经判定好每条记录是哪个动作**。

## 2. 两条路径，有先后

1. **事件自陈其动作。** 采集端逐条分类并把动作 id 写进 `kind`（`plugins/eventlog/event-schema.ps1`）。该 id 在目录中登记时，动作与目标类型都从目录读——**由一个地方决定**，日后新增动作不需要改这里。
2. **否则按记录自身的 id 映射。** 有些素材到达时没有分类过的 `kind`（契约夹具就是如此）。这些回退到参考适配器一直使用的同一张事件 id 表，**既有行为因此逐字节不变**——契约用例与演练输出重新生成后与仓库内容完全一致，已核对。

## 3. 身份键由类型驱动，不由适配器决定

事件的 `fields` 用的是 **Windows 事件自己的字段名**（`NewProcessId`、`TaskName`、`ServiceName`），不是目录的字段 id。两者需要在某处建立对应关系，本模块用一张表承担：每个类型 × 每个身份键 → 一列候选事件字段名。

**但键的清单来自类型，不来自这张表。** 表里没有的类型，其声明的每个身份键仍会被列出、取值缺失——而不是被悄悄丢掉。事件指名了进程 ID 却没说它何时启动时，身份就是**不完整**的，这正是身份契约早已为「不完整事件」准备的暂定结果（R03 边界样例第 3 条）。

当前有对应字段名的类型：`runtime.process`、`runtime.logon_session`、`runtime.terminal_session`、`runtime.module_instance`、`account.user`、`account.group_membership`、`startup.scheduled_task`、`startup.service`、`hardware.driver_service`、`hardware.disk`、`network.endpoint`。其余目标类型（文件、注册表路径、共享名等）的事件**动作照常产出**，只是目标在另一个来源补上缺失部分之前保持暂定。

## 4. 不做的事

- **不为未知 kind 发明动作。** 无法归属的事件保持未归属，并给出原因（回退路径沿用参考适配器的警告语义）。
- **不硬编码结果语义。** 动作的 `result` 读自目录声明。
- **不把只观察时间伪装成精确时间。** 素材说明来源未提供发生时间（`source_time_available` 为假）时，动作标为 `observation_only` 且不填 `occurred_at`。

## 5. 待办

1. **事件字段到身份键的对应表尚不完整**（第 3 节）。已覆盖的类型之外，目标保持暂定身份。是否需要补齐取决于那些类型的动作在真实链路上是否常用——**并入 S21，用真实采集输出核对事件字段名**（本机未做实测）。
2. **`phase` 在目录驱动路径上为 `None`。** 目录不声明阶段；回退路径沿用参考适配器按事件 id 给出的阶段（如 `task run`）。若模型希望阶段由目录声明，那是一次目录变更，不是适配器的判断。
