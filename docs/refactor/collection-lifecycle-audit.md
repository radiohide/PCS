# 采集全过程与成对变化审查（0.2.6）

[总评与整改顺序](collection-lifecycle-audit.md) · [101 类对象](collection-lifecycle-types.md) · [133 个来源](collection-lifecycle-sources.md) · [225 个采集定义](collection-lifecycle-items.md) · [可核对数据](collection-lifecycle-audit.json)

结论：原生采集已覆盖大部分当前状态，但“读取了清单”和“用户能看到完整的来去过程”之间仍有共性缺口。不能因为两种原始日志都被读入，就宣布安装/卸载、启停或开始/结果已经闭环。

本次逐项覆盖 **225 个定义、222 个开关、133 个来源、101 类对象、23 个日志通道、109 个日志分类**，未覆盖项为 **0**。当前来源归属为 127 原生、4 Hyper-V 兼容、2 汇总/导入。验证口径为源码审查与覆盖校验，不是 225 项真实操作验收。

0.2.6 已调整日常时间/读数的主时间线显示，防护更新合并摘要，修正随机密文导致的假变化；模块加载地址变化按用户要求保留。详见[验收记录](acceptance/routine-updates.md)。这只解决 G06 的部分可读性问题，其他过程缺口保留。旧运行观察以 0.2.4 为依据，不视为本版重新验收。

## 当前必须先补的四处

1. **首次出现**：此前只记入原始差异，没进入对象时间线；0.2.4 已补，首轮基线保持安静。
2. **再次出现**：同一个对象离开后回来，不能继续只认第一次看到。
3. **子项增减**：组成员、权限、浏览器策略、排除项、环境变量、ACL、文件流等，需要对子集合逐项差分。
4. **身份替换**：驱动版本等改变身份时，同一源行的 `object.changed` 要拆出旧绑定离开和新绑定加入，不能只等源行新增/删除。

这四项解决后，再做运行启停、操作结果和多来源关联。单例配置、采样、能力诊断没有自然的安装/删除对，应保留状态变化，不制造事件。

**另有已确认的 P0 生产断点 G12**：Sysmon 所有事件在原生采集器中统一为 `execution.sysmon_event`，后端回退映射不支持该提供程序，目录里的事件动作没有参与改写。于是进程启退、驱动/模块加载、连接、文件创建/删除虽有界面分类，当前不能据此认定已进入对象行动。验收必须用原生实际信封，不能只用手工填写精确 action kind 的测试材料。

## 驱动应拆成五层

| 层次 | 加入端 | 移除/结束端 | 当前状态 |
|---|---|---|---|
| 驱动仓库包 | 仓库中新增包 | 仓库不再列出该包 | 原生 DISM 已有全清单；0.2.4 接通首次出现；重复加入、安装过程仍缺。身份为 INF＋仓库路径。 |
| 驱动服务登记 | 服务登记加入 | 服务登记移除 | 原生 Win32_SystemDriver；清单对不等于驱动包安装/卸载。 |
| 设备驱动绑定 | 设备绑定到版本 B | 旧版本 A 绑定解除 | 设备 ID 不变时原始行是 changed；A→B→A 必须专项补齐，列为 P0。 |
| 运行状态/加载 | 驱动开始运行；Sysmon 6 加载日志 | 驱动停止运行；真正卸载事件 | 原生 State 可作字段对比；Sysmon 加载事件还存在 G12 生产断点，也未接对应卸载事件。 |
| 安装操作 | 开始安装/更新/卸载 | 成功、失败、回滚、需要重启 | 当前没有 SetupAPI 安装过程解析；UMDF 通道已读原始日志，尚未实现包级结果关联。 |

用户时间线建议分别显示“新增驱动包”“仓库中已无此驱动包”“设备驱动：A → B”“驱动已开始运行／已停止”“驱动安装失败（原因）”。只有明确操作结果才写安装/卸载成功。多个包共享 INF、包存在但未绑定设备、设备已移除但包仍保留、安装失败回滚都要单独验证。

## 成对过程的统一判定

- **清单增减**：以前完整清单无该对象、这次有，显示新发现；同范围完整清单从有到无，按类型显示离开/移除。首次基线不当新增操作。
- **状态变化**：运行/停止、启用/停用、健康/故障、连接/断开，记录同对象的前后值；未知和读取失败不参与开关判定。
- **操作过程**：开始、成功、失败、取消、回滚按来源分别记录。同次操作用明确的 ActivityId/TaskInstanceId/包或设备身份关联，不按“时间差不多”硬配。
- **重现与版本**：再次出现要记录重现；确认终结后按代际建新实例。A→B 是替换还是并存由实际身份/产品锚点判定。
- **来源关系**：同一对象多个来源可以互补。一个来源读失败/禁用、一个 COM 角色移除，不使整个对象消失。
- **时间**：快照仅给出两次完整检查之间的区间；有明确日志时间才用精确时间。界面的 30 秒时间分组只影响排版，不合并成同一次操作。
- **模块文件**：sihost 等目标仍融入进程/模块/文件体系；成功观察模块后跟踪磁盘文件变化，校验失败/缺失/恢复是文件状态，不能直接认定进程启动失败原因。

## 环境与性能约束

继续采用原生后端采集；127 个原生来源失败后不回退 PowerShell。四项 Hyper-V 等有环境再迁移。普通/增强权限、当前用户/机器范围、已启用日志与可读保留历史分别记录。CNG 某提供程序失败只阻断该提供程序/范围，不能移除其旧密钥；无 Docker、无电池、无 Hyper-V 等按环境能力处理。

状态差分只比较同范围、完整、成功且开关启用的相邻集合；绑定与水位持久保存，重发/重启可去重。优先使用变化通知唤醒有界复核，单个来源上轮完成再安排下轮；文件抖动合并、稳定后复核，排除历史数据库/WAL/SHM 和程序自身产物。不得为配对逐对象启动 PowerShell，不通过高频全盘/全注册表轮询补另一端。所有新事件流需有每轮预算、队列上限、背压与断点。

本轮部署后的只读运行观察还发现**投影吞吐与维护写入调度缺口**：一次来源统计中，Shell/COM 登记有 42,302 条待处理，多个来源同时积压；失败数为零，但分批历史新增恢复多次因后台写入忙退避。尚不能把此现象认定为循环采集，需专项测量每轮完整观察的入队量、处理吞吐与稳定收敛，并评估无变化观察的批处理和公平写入窗口。现阶段不能将旧历史回补标为全部完成，也不应靠缩短重试间隔掩盖问题。

本次额外恢复客户端已停止，持久游标保留在 3,584，检查时最新原始记录序号为 88,252；这是恢复进度标记，不是成功恢复条数。正常增强采集与界面继续运行。此运行限制单列保留，先解决吞吐/写入调度后再完成剩余回补。

## 核对依据与复核命令

采集定义/开关来自 `collection-catalog.json` / `collection-controls.json`；来源和对象来自 `model/sources.json` / `model/catalog.json`；原生归属来自 `native-migration.json` 和实际 emitters。通用新增/缺席、子对象、日志动作分别检查 `crates/storage/src/projection.rs`、`identity.rs`、`evidence.rs`、`crates/contracts/src/adapters/event*.rs`、`source_gaps.rs`、`reference.rs`。前端事件标题和当前状态文案分别检查 `event-semantics.js`、`type-presentation.js`，不将已有标题计作后端配对完成。

运行 `node scripts/build-lifecycle-audit.cjs --check` 核对输入摘要、133/225/222/101 的完整覆盖和全部生成表；输入改变时需重新审查并运行不带 `--check` 的生成命令。该命令仅检查清单一致性，不替代驱动安装、会话、文件或虚拟化实际流程验收。
