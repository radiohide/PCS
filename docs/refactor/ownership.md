# 代码与目录所有权（R07）

日期：2026-09-12。清单：`model/ownership.json`；检查：`scripts/check-ownership.cjs`。

依据：[并行开发前置条件与准入方案](parallel-readiness.md) R07。类型边界表：[并行类型与来源边界表](parallel-boundaries.md)（由 `model/catalog.json` 生成）。

**所有权指改动整合责任，不限制必要的跨模块修复。** 一个人修别人范围内的一个 bug 是正常的；需要协调的是会改变契约、结构或生成结果的改动。

## 1. 四条工作线与一条既有实现

| 工作线 | 主责范围 | 不应自行修改 |
| --- | --- | --- |
| 基础数据线 `base-data` | 存储实现、契约参考实现、类型边界生成 | 前端展示规则；其他类型专属的来源解析 |
| 类型适配线 `type-adapters` | 样例与夹具、各来源适配器（预留 `crates/adapters/`） | schema 编号；最终对象 ID 算法；公共枚举 |
| 查询与界面线 `query-ui` | IPC、界面、前端检查 | 原始证据语义；适配器私有格式 |
| 迁移验证线 `migration` | CLI、回放与对账工具、存储示例 | 运行库数据；用户配置；未协调的保留规则 |
| 既有采集运行实现 `existing-runtime` | 服务、监督进程、现有采集插件、既有检查脚本 | — |

**第五条不是并行方案里列的。** 方案只列了四条工作线，而服务、监督进程、现有采集插件与既有检查脚本不属于其中任何一条。单列出来是为了避免出现无人认领的空白——文件无人认领时，改动就没有协调对象。这一条在清单里标注为「不属于本次四条工作线」。

## 2. 文件责任表由检查强制

`scripts/check-ownership.cjs` 枚举仓库中**已跟踪与未跟踪且未被忽略**的全部文件，强制：

1. **每个文件恰好被一处认领**（一个工作线或一个共享入口）。被两处认领会报错——这正是重叠归属该暴露的地方。
2. **每个主责范围至少匹配一个文件**。声明了一个不存在的目录会报错，避免范围写错后无人发现。
3. **预留范围必须确实为空**。`crates/adapters/` 是给类型适配线预留的；一旦里面出现文件，检查会要求把它从 `reserved` 移到 `owns`。

未跟踪但未被忽略的文件**也在枚举范围内**：一个新文件正是最需要被认领的时刻，等提交之后才发现就已经晚了。

## 3. 共享入口

四处共享入口，各有**唯一整合责任人**：

| 共享入口 | 整合责任人 | 生成器 | 规则 |
| --- | --- | --- | --- |
| 中立模型目录 `model/**` | 基础数据线 | `scripts/check-model-catalog.cjs` | 只改 `model/*.cjs` 编写源，随后运行生成器；版本号在 `vocabulary.cjs` 与 `contracts/src/model.rs` 两处，必须一起改 |
| 公共契约（adapter / identity / semantics / query / model 及契约示例） | 基础数据线 | — | 破坏性变更先停止依赖旧语义的集成，再统一升级；只增加兼容字段时更新版本与样例 |
| 数据库 schema 与迁移号 | 基础数据线 | — | 结构在 `model.rs` 定义、迁移块在 `lib.rs` 执行，同属一个整合责任人 |
| 契约检查 | 基础数据线 | — | 添加与放宽都要说明理由；不得为了让某次改动通过而放宽既有规则 |
| 文档与仓库元数据 | 基础数据线 | — | 验收记录不改写已提交的历史结论 |

共享入口的文件**不列在工作线的 `owns` 里**，避免一处文件被两处认领。工作线要改共享入口时走第 4 节的登记流程。

## 4. 共享改动登记格式

任何对共享入口的改动，先登记一条记录，再改代码。位置：`docs/refactor/shared-changes/NNNN-<slug>.md`，编号递增、不复用。

```markdown
# NNNN <一句话标题>

| 字段 | 内容 |
| --- | --- |
| 共享入口 | 中立模型目录 / 公共契约 / schema 与迁移号 / 契约检查 / 文档 |
| 整合责任人 | 哪个工作线 |
| 提出工作线 | 哪个工作线提出 |
| 变更类型 | 兼容增量 / 破坏性变更 |
| 影响的工作线 | 逐条列出 |

## 问题
为什么现有约定不够用，具体到哪个文件、哪条规则。

## 旧结构 / 新结构
两者并列写清，包括受影响的 ID、枚举或时间语义。

## 兼容性
旧消费者会怎样。兼容增量要说明旧消费者忽略新字段的真实处理能力；破坏性变更要说明停用与升级顺序。

## 样例变化
哪些样例、生成物与固定响应集需要一起更新。

## 数据迁移
是否需要迁移既有数据；若需要，说明由谁在哪个步骤执行。

## 检查结果
改动后实际跑过的命令与结果。
```

**为什么不限制得更细**：登记的意义是让依赖方知道契约变了、以及自己要不要动。它不替代集成验证，也不要求事前审批——发现问题时补记同样有效，只要在合并前完成。

## 5. 机器可检查的三条验收

计划 R07 的验收里，三条可以机器检查，`check-ownership.cjs` 逐条强制：

| 验收条件 | 强制方式 |
| --- | --- |
| 重叠类型只有一个主实现归属 | 每个目录类别一个实现步骤（S09–S20）；每个来源恰好匹配一条适配器归属规则；某个来源产出的类型跨多个类别时，适配器仍只有一个归属 |
| 无人自行分配迁移号 | 只有声明路径内的文件可以写 `PRAGMA user_version`；声明路径本身也要确实在写（防止声明过时） |
| 生成目录不手工修改 | 每个生成物登记其生成器，且生成器文件必须存在 |

**已实测会失败的注入**：新增一个无人认领的文件、在声明路径之外写 `PRAGMA user_version`、删掉一个类别的类型归属——三者都使检查以非零码失败并指出具体对象。

### 5.1 适配器归属的默认精确匹配

适配器归属规则默认**精确匹配**，只有以 `.*` 结尾的规则才做前缀匹配。这一点是注入测试逼出来的：最初允许隐式前缀，于是 `pcscope.software` 把 `pcscope.software.appx-user` 也认领了，一个来源出现两个归属。显式前缀消除了这种歧义。

## 6. 尚未覆盖的

- **文件责任表只到目录与文件级别**，不细分到函数或结构体。四人规模内够用，工作线数量增加时需要更细的边界。
- **分支与目录隔离未定义**。R08 负责工作区与集成策略；在它完成前，所有权只是「谁负责协调」，不保证并发修改不冲突。
- **登记是流程约定，不是机器门禁**。检查不验证共享改动都有登记条目；是否补齐靠评审。
